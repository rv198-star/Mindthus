## Frame Fitness

The post-release changes are not a patch-level TPlan bugfix. They add a public explicit
skill, new versioned data contracts, local case packaging, and test governance.
Therefore the correct release target is a minor release, `v1.6.0`, not another
`v1.5.x` patch.

TPlan runtime identity is a separate object. No file under `skills/tplan/scripts/` and
no TPlan fingerprint file changed after `v1.5.4`. TPlan runtime provenance treats
`package_version` and `source_id` as compatibility identity. Mechanically changing the
TPlan runtime manifest to 1.6.0 would make existing v1.5.4 Missions incompatible without
an actual runtime change. The release distribution is therefore 1.6.0 while the TPlan
runtime generation remains `1.5.4` / `mindthus-v1.5.4`.

## Findings And Corrections

### F1 — Release identity still declared 1.5.4

Severity: Blocker

Observed:

- plugin/release builder version was still 1.5.4;
- installed runtime logger version and cache fallback were still 1.5.4;
- README called the checkout v1.5.4 despite substantial new public capability;
- no v1.6.0 release-candidate note existed.

Correction:

- changed release builder and runtime logger distribution version to 1.6.0;
- prepared `docs/releases/v1.6.0.md`;
- moved the post-v1.5.4 changelog into a v1.6.0 candidate section;
- updated release and packaging contracts;
- retained public download links to the actually published v1.5.4 Stable until tag and
  assets exist;
- retained the unchanged TPlan runtime generation at 1.5.4.

Result: closed.

### F2 — TPlan case preparation was not strictly read-only

Severity: High

Observed:

`prepare_tplan_case` read an atomic outcome-attribution snapshot, then called the normal
`build_mission_pulse()` path. The normal TPlan read path may recover a pending Mission
transaction before returning. Case preparation could therefore mutate the Mission while
claiming to be read-only.

Correction:

- case-prep now performs one `read_outcome_attribution_snapshot` call;
- it derives a bounded `tplan.case-pulse-view.v1` from that same snapshot;
- it does not call normal Mission Pulse runtime reads;
- pending Mission transactions fail closed and remain untouched;
- tests compare every Mission file before and after export and exercise the pending
  transaction boundary.

Result: closed.

### F3 — Release/runtime identity could have been over-coupled

Severity: High if implemented incorrectly

Observed risk:

A conventional release bump would also update `skills/tplan/resources/runtime-manifest.json`.
TPlan compatibility code explicitly treats that version and source ID as identity, so
such a bump would reject existing Missions.

Correction:

- release tests now lock plugin/distribution manifests to 1.6.0;
- the same tests lock the packaged TPlan runtime manifest to 1.5.4;
- release documentation explains why this split is intentional.

Result: closed by explicit contract.
