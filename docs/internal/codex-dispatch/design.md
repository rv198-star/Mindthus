# Codex 多模型会话派工：设计草案

状态：v0.1 修订 1，2026-11-18。根据首批真实派工回写宿主接入、确认与对账约定。配套[功能草案和验收场景](requirements.md)、[主会话验收记录](owner-acceptance.md)。

## 核心分工

由主会话 A 读取当前环境、比较会话组合，把选择交给用户，再按确认的范围派工。接手方在自己的职责内解决问题并提交成果与设计偏差；A 对最终目标、采用哪个版本和下一步负责。首版交付形态拟为一个 Codex Skill，主规则放在 `SKILL.md`，宿主接口细节按需读取。选型和分工由 A 判断，读取清单、核对型号和档位可以机械校验。

| 载体 | 适用工作 | 结果如何回来 |
|---|---|---|
| 当前会话的 SubAgent | 短时调查、比较、查证；遵循宿主的委派和上下文继承规则。在 TPlan 下遵循[只读调查约定](../../../skills/tplan/resources/subagents.md)。 | 返回主会话，由 A 核实和整合。 |
| 独立 Codex 会话 B/C | 设计、实现、审计需要保留各自上下文，或用户要求不同模型相互制约。优先复用能承担本轮职责且已获准联络的会话。 | B/C 用自然语言交付；默认由 A 读取结果，避免另发回执。 |

## 1. 先取目标环境清单

进入会话配置后的第一个外部动作是读取清单。先从任务上下文确定载体、目标宿主和提供方。对 Codex App Server，分页读取 [`model/list`](https://learn.chatgpt.com/docs/app-server#list-models-modellist)：默认只取可见项；指定提供方时传 `modelProvider`，沿 `nextCursor` 读完。记录宿主、提供方、读取时间，以及每项的型号 ID、显示名、`supportedReasoningEfforts`、`defaultReasoningEffort`。同一批、同一环境可共享本次结果。

如果派工工具自身公布了适用于目标的型号和档位，将其作为直接可选范围；两种来源同时可得时，只推荐目标清单和该派工入口均支持的组合。取不到 App Server 时可用目标工具明确公布的范围。两者都取不到时标记“待核实”，提示用户指定可核验的目标环境或保留方案；公开网页只用来补能力信息。跨主机分别核对，临时子代理也使用自己的工具约束。

本机 2026-11-18 的只读样本有 13 个可见型号：DSF 4.1 Flash 支持 low 到 xhigh，Sol 6.2 和 Astra 6.2 还支持 max，后二者的默认档也不同。这个样本解释了为什么要读清单；技能包内不维护这 13 项的副本。

本批实际走通两种接入：临时启动的 CLI App Server 从标准输入输出收发 JSON 行；本机已运行的 managed App Server 经已核实的 Unix socket，以 WebSocket 承载同一组 RPC。后一种接入的 Python 依赖及读法见[宿主操作](../../../skills/codex-dispatch/references/host-operations.md)。接入不可用时退回同一目标已公布的工具清单，保留该清单的来源和适用范围。

## 2. 补足会改变分工的能力信息

A 先写出本批真正需要的能力，例如“依照已冻结契约批量实现”“自行追查跨模块故障”或“独立发现验收遗漏”。用户的明示偏好约束选型；已有同版本、同类任务的结果优先用于判断适配度。清单能回答“可选什么”，默认档可作起点，具体任务决定是否提高或降低推理投入。

当一个疑点会改变角色、首选、替补或推理档，而手头证据不足时，**对本批候选集中做一轮联网查证**。用公开的模型名、版本和能力问题检索；优先取官方模型卡、发布说明，其次取任务和版本可比的公开评测。资料只留“来源链接、适用版本、哪项选择因此改变”。私有路由别名无法对应公开版本时保留未知，不把内部地址或任务内容发给搜索服务。

一轮后仍有分歧或网络不可用：标明哪项能力待验证，把证据充分的组合放在前面，用户也可以用自己的经验改选。例：已知 X 支持 high，但缺少它做独立审计的记录，可将 X 放在待验证的自定义建议里；审计是硬要求时，优先推荐有相应依据的候选。

## 3. 组合、提示与确认

每套方案只需要回答四个问题：

- **谁做什么：** A 的当前职责与型号、B/C 各自负责的工作，哪些工作并行、哪个版本交独立审计。已有会话注明名称及复用方式；新会话列出拟建角色、宿主、工作范围和通信方向。
- **谁来接替：** 每个会话给出“首选型号 + 推理档”，再列一至两个有顺序、能承担同一职责的“替补型号 + 推理档”。同一型号的不同档位只算一个型号。缺合格替补就标明缺口。当前 A 的替补是交接预案；切换正在工作的主会话另按宿主交接。
- **为什么值得选：** 两至三套可行方案以一次具体取舍区分，例如把排障预算留给实现方，或把独立推理预算留给审计方。用户要求独立或异模型审计时，首选和替补都要维持该条件。只有一个可行组合就展示一个，并保留自定义入口。
- **确认会触发什么：** 提示列出本批将创建或联络的会话、允许的工作及切换条件。优先使用当前模式支持的原生选择控件，展示推荐项并允许自由文本；否则在对话中给同样的选项。多项细节先在一张表讲清，控件只负责选择。

默认在首次派工前等用户明确提交选择。部分指定视为锁定相应字段，补齐其余项后展示；用户完整指定并明确要求执行时，校验通过即可派工。用户改选合法档位且明确“其他照旧，开始”，以这条回复为准。若自定义选择不可用，说明是哪一项，给出最接近的可用选项，等待决定。没有回复或选择“暂不派工”时停在方案阶段。

确认可以覆盖整个批次和已列明的替补。创建独立会话、向另一会话发消息仍需相应的用户明示授权：已有授权直接沿用；若选择只表达了模型偏好，保留该选择，只补缺少的通信授权。新增接收方、扩大写入范围或放宽验收，需要单独确认相应变化。

按当前模式检查控件可承载的输入。仅用于收集偏好的控件仍可选组、改档；缺少的通信授权在主对话取得。异步控件返回“已展示”和用户实际提交分开记录。

## 4. 派工、替补与审计

每份派工说明包括：本轮目标、基准设计与输入版本、可写范围、可自行决定的事项、验收条件、交付位置和重大冲突的回报路径。接手方只拿完成职责所需的上下文。独立审计方拿固定版本、原验收条件和必要事实，自选检查方法；实现方的自测可以作为线索。

在 Codex 桌面端，临时委派走 `spawn_agent`；当前接口完整继承上下文时沿用主模型和推理档，需另选型号或档位时给子代理独立上下文和必要材料。独立会话走另一组工具：明确需要新建时用 `create_thread`，给已有会话派新一轮用 `send_message_to_thread`，结果由 A 用 `wait_threads` 等待，必要时用 `read_thread` 核对。新建时已随首条提示派出的任务，不再另发一遍。

新建可能先返回待建引用 `clientThreadId`。A 保留该引用，在原宿主找到对应的正式 `threadId` 并核对首轮任务后，再用正式引用等结果。若响应完全丢失，同样按原宿主、目标与任务说明对账；尚未查到时保持原意图待定。

A 将已确认的型号和推理档用于目标会话的新一轮执行，保存原生会话或轮次引用。已有轮次还在运行时先核对其状态；宿主可回读实跑型号和档位时按该轮记录，未暴露则分别写“已请求”和“实跑未核实”。[上版实测](../tplan-collaboration/reviews/host-live/audit/actual-sol-model-recovery.json)中，运行中收到的切换指令和后续实际采用新型号的轮次是两回事。

| 情况 | A 的动作 |
|---|---|
| 服务拒绝、额度耗尽等已确认失败，原执行没有在途写入 | 先看原执行留下的产物，再按确认顺序取仍合格的替补，沿用职责、输入版本和授权范围；在批次反馈中注明原因、实际型号和档位。锁定型号未获替换授权，或所有合格替补耗尽时，只就缺口返回用户。 |
| 发送超时、结果未知 | 保留原派工意图，查询同一目标。弄清是否已执行，再判断是否需要替补。 |
| 实现遇到技术难题或审计发现缺陷 | 按下一节处理设计偏差，或由原实现方返修。复审针对新交付版本；模型服务正常时，不以改换审计人代替返修。 |

## 5. 自主执行与设计偏差清单

交互有成本。默认按批回报，由接手会话自行定位、尝试和验证，不按分钟轮询。多条实现路径都满足设计时，接手方可自行选择。不同模型的差异体现在派给它的范围、预期排障深度和交付证据；提高推理档只改变投入，授权范围沿用原约定。

实现没有遵循一条已经正确的规则时，自行修复、自测，作为正常交付。**实际情况与基准设计有差异**时，在本批清单增加一行。能在授权内解决的先解决，随交付统一反馈；若继续将迫使团队改变目标、共享接口、验收条件，或使另一会话正在依赖的设计失效，立即回报“事实与证据、影响范围、需要谁决定什么”，仅暂停受影响部分。

| 基准设计与原约定 | 实际偏差及证据 | 接手方处理与验证 | 设计方处置 |
|---|---|---|---|
| v1 要求读取全量；方案按单页写 | 第 101 条起由下一页返回，附分页样例 | **执行已解决**：遍历至游标为空，跨页用例通过 | **待回写**：建议把终止条件纳入设计及验收；采纳后关联新版本 |
| v1 要求可回放完整历史 | 源端只存最近 100 条，附接口保留规则 | **需上游决定**：全量回放部分暂停，其他工作继续 | A 决定补历史来源，或提请用户修改覆盖目标 |

一份交付可以是“执行已解决，设计待回写”。设计负责人按批将每项落为“已更新（版本/位置）”或“保留局部例外（原因/适用范围）”；A 把相关变更带入随后的派工与审计。接手方不必为每一条等回执。

## 6. 记录归属与首版验证

单独使用时，A 在已有任务文档或本次交付里保存一份批次记录：确认的组合与授权来源、设计版本、会话/产物引用、偏差清单及设计方处置。首版不需要常驻调度器、模型排行榜或独立数据库。

在 Codex 的 [TPlan 协同](../../../skills/tplan/resources/collaboration.md)中，正常入口经 Codex 适配进入**实际安装的 Dispatch**。同一个 A 从 Mission 带入目标、当前合同和用户授权。Dispatch 负责载体、清单、选型、已有授权校验或一次组合确认、原生派工与回执流程；A 仍是唯一 writer，决定采用、返修或等待。组合和偏差清单作为关联材料，不另建状态；普通 B/C 无需安装 TPlan。

新 runtime 在原[协同协议](../../../skills/tplan/resources/collaboration-protocol.md)上增加可选的原生绑定能力。已知会话沿用绑定；新建会话先登记逻辑参与者（目标宿主已知，正式会话 ID 为空）。两种路径都先准备意图并占用一次派工，再调用宿主。原生回执带来的待建引用仅用于对账；有正式会话、目标宿主和这次派工的证据以后，A 原子绑定并登记发送确认。早到反馈先保留，核对以后用同一来源记录关联；错来源、旧轮次和未知发送留在原历史中。替补必须等原执行明确无在途写入，并使用已授权的后续轮次。

在途 Mission 使用原 writer。旧 writer 可按原合同配合 Dispatch 派发给已知会话；需要晚绑定的创建要用具备该能力的新 Mission，既有 Mission 不偷偷切换 writer。非 Codex 或无协同沿用原流程。

实现后按功能草案 F1–F8 走查。至少在真实 Codex 宿主观察一遍“取清单 → 显示两组方案 → 用户自由改一个档位 → 只执行确认的组合 → 带偏差交付”，另查一次取消后零派工、一次发送未知时不产生第二个写入者。验收保留用户实际看见的提示、宿主返回的轮次和设计回写位置。

设计参考：[Codex Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)说明载体的模型、推理档和上下文；[Anthropic 多代理实践](https://www.anthropic.com/engineering/multi-agent-research-system)支持在派工时写清目标、输出和范围；[Intelligent AI Delegation](https://arxiv.org/html/2602.11865)区分授权程度和监督方式。具体模型搭配由本批证据与用户选择决定。
