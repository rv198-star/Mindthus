# 请求

/mindthus:explain --eli5 --audience 产品负责人 解释以下概念。

# 源材料

在这个示例数据库里，每笔事务读取开始时的一份一致数据视图；这让它不会看到别的未提交事务的半成品，但不保证多个事务组合后的所有业务规则都成立。示例规则：医生A与医生B至少一人值班。两个事务都读到两人值班，分别把A和B设为不值班；它们改不同记录，因此示例系统允许两者提交，最终无人值班。这里称为写偏斜。示例采用对该业务规则的专门同步来防止这一结果；不是所有数据库、隔离级别和规则都需要同一种办法。这里只解释这段材料，不提供具体数据库配置。

# Explain输出

**两次排班修改各自看着可行，合在一起却可能让“至少一人值班”的业务规则失效。**

把这个示例里的每笔事务想成拿着一张“开始读取时的排班表快照”办事。这张快照是一份一致的数据视图，不会掺入其他事务尚未提交的半成品。但几笔事务一起修改后的最终排班，仍可能违反业务规则。

看看医生 A、B 的例子：

1. 规则要求两人中至少一人值班。两个事务都读到 A、B 在值班。
2. 第一个事务把 A 设为不值班；按它读到的表，B 还在值班。第二个事务把 B 设为不值班；按它读到的表，A 还在值班。
3. 两个事务改的是不同记录，示例系统允许它们都提交。最终 A、B 都不值班，业务规则被破坏。

材料把这种情况称为**写偏斜**。对产品负责人而言，需要理解的区别是：读到一致的数据视图，并不保证多笔事务组合后的业务规则仍成立。

这个示例用针对“至少一人值班”这条规则的专门同步，防止最终无人值班。其他数据库、隔离级别或业务规则未必需要同一种办法；这里不涉及具体数据库配置。
