# #211 v0.3 实现与用例审计

审计基线：`5985bd2c7b5d87ecebeabdbafe41add4d354e818`，分支 `experiment/typed-decision-runtime`。
设计基线：[REPAIR-DESIGN.md](REPAIR-DESIGN.md)。比较范围：设计提交 `27535575a` 之后的实现，
以及被新入口调用的旧运行时、宿主适配器和现有测试。日期：2026-09-26。

**结论：部分重新实现，尚未完整落实新设计。存在确定的运行阻断、消费与恢复缺陷；
新增 v0.3 自动化测试尚未编写，五条件比较也未接齐。当前不具备进入真实比较的工程条件。**

本轮为静态代码与用例审计。下列路径由源代码推演，未执行测试、复现脚本或实验模型请求；
不把静态推演写成实测失败。审计者是本任务当前 Codex，不称独立模型复核。
仅新增本报告，未修订实现、旧用例、账本或分数。后续路径问题中，F02–F09 有些须先修 F01
才能在完整入口走到；它们仍是代码已存在的缺陷，不能因上游先报错就视为不存在。

## 确认已写入的部分

- `entry.run` 和 CLI 增加 `route-control.v0.3`；沿用原 Episode 与 CurrentAgentHost。
- 薄输入中加入 conversation、host_inferences、intervention 与事前消费政策。
- S0 增加事项/候选覆盖题；S1 对真实输出绑定四个维度，保留多条 finding。
- ②增加逐项修正/异议/未决合同、一次复查及终态接受合同；接收使用原 execution 额度。
- 官方 TypeSafe `jev-1.13.0`、本地参数、新运行身份与旧账本隔离均有明确入口。

这些是代码存在性的结论。下面的缺陷使“已接线”不能等价于“链路可完成”。

## 需要修复的实现问题

### F01 · P1：S1 步骤未登记，所有产生 S1 记录的正常路径都会卡在计账

位置：`route_control_v03.py:21`、`:350`、`:377`；`route_control.py:27`；
`relationship_runtime.py:125–129`。

新模式直接使用旧 `STEP_KINDS`，其中没有 `candidate`。但初检写入 `steps/candidate`，
复查写入 `steps/candidate__recheck`。Episode.tally 对目录名取 `__` 前缀，遇到这两种
记录都会以 `unknown_episode_step_kind` 拒绝；纠偏、接收、finish 和后续恢复都要调用 tally。
因此至少在 S1 返回后，正常链路无法继续。这不是 Jev 语义问题。

最小修复：为新模式登记统一的候选判断步骤类型，或采用现有已登记名称；保留判断额度。
应补用例：从公共 entry 走完 S0→真实形状的宿主回执→S1→接收，以及纠偏复查分支；
断言正常计数、完成恢复、不新增重复请求。

### F02 · P1：①没有收到 S1 建议，也没有采用建议后修订的机会

位置：`route_control_v03.py:348–356`、`:419–428`；`source_direct_v03.py:317–325`。

只有 `committed` 进入纠偏宿主步骤。`advisory` 直接把事项标成 resolved，随后发送
禁止改写的 acceptance 请求；该请求只有原输入、候选 hash 和粗状态，没有 S1 观察。
原先的执行请求发生在 S1 之前，也不可能消费这次观察。①实际是“生成后检查并存档”，
缺少“把发现作为建议交给宿主、由宿主决定采用或忽略”的行为。

S0 的覆盖观察也只存放在 route.coverage，执行请求没有携带该部分；①不会因覆盖结果
改 row，因而这类建议也未完整传递。直接比较当前①／②会把是否有后续处理机会混入政策效果。

最小修复：交付同版观察，①允许自由采用/忽略及一次有界修订，不强制逐项处置；②保持义务。
应补用例：①看到同一命中，可选择保留，也可修正并复查；两者都记录最终产物与实际消费。

### F03 · P1：独立仲裁缺少正在裁决的候选正文

位置：`source_direct_v03.py:283–295`、`:200–214`。

仲裁请求传递 objections、findings 和 original_input，却没有 correction_request.candidates，
也没有修订文本。finding 仅有 target_version/hash，没有候选正文。真实候选在 S0 后生成，
并不在 original_input 中。独立上下文无法仅凭 hash 判断这条断言是否越界或异议是否成立；
若依赖执行宿主的隐含记忆，又不再满足独立上下文条件。

最小修复：绑定并交付被异议的原候选正文、实际比较材料和必要的新版本，明确裁决适用版本。
应补用例：从干净上下文读取仲裁请求即可定位原断言；旧/新候选或 hash 不匹配时拒绝。

### F04 · P1：仲裁成功后的再次恢复会跳过已完成裁决，改变接收请求

位置：`route_control_v03.py:387–416`、`:425–430`；`current_host.py:148–155`。

代码在 `counts['arbitration'] >= 1` 时直接标记 arbitration_not_supplied，不区分“额度已由
本请求使用且已有结果”和“需要再发新请求”。实际 handoff 路径是：提交仲裁回执→恢复并
消费裁决→导出接受请求→提交接受回执→再恢复。最后一次 tally 已计入一次仲裁，代码跳过
原裁决，改成 unresolved；随后的 acceptance request 与已经落盘的请求不同，触发不可变记录
冲突，或错误保留未决。

最小修复：先恢复完全相同的已完成仲裁；仅对新请求检查剩余额度。
应补用例：跨独立仲裁和最终接收的多次 handoff 恢复，结果与请求字节保持一致，仲裁只计一次。

### F05 · P1：接受前置后的旧版复查会清掉新版覆盖阻断

位置：`source_direct_v03.py:146–149`；`route_control_v03.py:157–165`；
`route_control.py:413–422`。

消费者因 COVERAGE.missing/unclear 被置为 delegated_unresolved；当其依赖产物被接受，
新 dispatch 直接调用旧 `_after_artifacts`。旧函数只编译/消费原方法题，并用新 row 覆盖旧
row；没有重新检查或保留 v0.3 覆盖义务。若旧方法题给出明确主方法，消费者便恢复 committed，
即使缺失的方法/事项完全没被补齐。旧根因修复本身保留了，但新覆盖约束没有接入它。

最小修复：复用后继定点复查时保留所有未被新证据解除的 v0.3 义务，并维持新模式合同身份。
应补用例：前置被接受只能解除真正由该产物解决的依赖；覆盖缺失和其他未决仍保留。

### F06 · P1：前置产物被修正后，依赖旧版本的后继仍可被一起接收

位置：`route_control_v03.py:210–227`、`:346–350`、`:367–376`、`:425–430`。

dispatch 先让前置被接受并供后继执行，整批输出生成后才运行 S1。若 S1 修正前置，代码更新
前置 text/hash，却保留旧 accepted_uses，也没有使基于旧前置产生的后继失效。复查只包含
revised_issues，未修改的后继不重判。最终可能接受一个新前置和基于旧前置的后继组合。

最小修复：确定候选版本稳定后再接受为依赖，或在前置改变时将真正受影响后继标未决，按原
预算完成必要复查/重执行；不能沿用旧 hash 的用途接受，也不能给整图重新开预算。
应补用例：前置改变决定性结论，后继必须失效；无依赖事项不受影响；预算不足明确保留未决。

### F07 · P2：辅助未知局部化仍沿用旧逻辑，尚未实现

位置：`source_direct_v03.py:130`；`route_control.py:253–277`、`:287–293`。

新 S0 消费完全调用旧 consume。任一候选的适用性/角色未知仍进入 reasons，使主方法不能
提交；SELA/MPG 伴随观察未知还会直接清空已定主方法。新题组没有区分“仅辅助贡献未知”
与“主路线确实依赖它”的作用范围题或等效合同。因此设计 §2.1 的关键替换没有发生。

最小修复：在观察前固定必要性/依赖语义；仅辅助未知保留为报告，不无条件撤销明确主路线。
应补用例：明确主方法＋辅助未知继续；真正冲突/必要依赖未知阻断；无法判定作用范围时未决。

### F08 · P2：①／②拿到的方法材料不同，比较会混入额外因素

位置：`route_control_v03.py:182–198`；设计 §2.2、§3.3。

①加载全部 canonical 方法，②只加载选中方法和 mandatory_reads。因此两种方式除消费政策外，
模型可见上下文也不同，不能直接归因为建议式与约束式的差别。①可自由改路是必要能力，
但实现这项自由不能使对照材料失配。

最小修复：比较时冻结相同可见材料与上限，再由①／②分别消费；额外读取的实际工作如另测，
单列为整包效果。应补用例：同输入两个 handoff 的材料摘要一致，区别仅为事前声明的消费规则。

### F09 · P2：最终接收没有形成设计要求的终态

位置：`source_direct_v03.py:317–343`；`route_control_v03.py:303–319`、`:425–439`。

acceptance_request 仅传候选 hash 和 issue 级状态，未绑定完整检查/复查/裁决及剩余 finding
状态。宿主返回 accepted=false 是合法回复，但 run 只保存 reply，不将拒绝加入 pending 或
终态原因；可以得到 reason=null、pending={}、accepted=false 的组合。设计要求的
resolved_by_revision、resolved_by_objection、technical_failure/unrun 等逐项状态也未实现。
固定 task_complete=false 确实避免自动宣称语义成功，但不能代替可用的消费终态。

最小修复：接收绑定实际候选和相关检查/裁决身份；根据拒绝、未接收及每项义务生成明确终态，
消费完成与语义正确仍分开。应补用例：接受、拒绝、无额度、混合事项部分接受均有一致可恢复状态；
同事项多发现分别修正/异议时，必须按实际候选版本判断裁决适用性，不能用对旧候选的解除
自动清掉新候选的命中，也不能把有效解除的信息丢失在一个 issue 布尔状态中。

从 `27535575a` 到审计 HEAD 的改动中，**没有任何 tests 文件新增或修改**。
搜索 tests 没有 `route_control_v03`、`source_direct_v03`、`route-v03` 或新入口模式的实际调用。
现有 fixtures 仍是 `c01-sra.json`、`entry-correction.json`、`route-control.json`，没有新薄输入用例。

`tests/test_current_host.py:37–39` 始终使用旧 `route_control.MODE`；该文件中的 Skills/显示
测试使用旧 relationship proposal。`tests/test_observation_assessment.py:9` 导入的是旧
observation_assessment；`:78–95` 还在验证旧版 evidence 单项优先规则。这些测试应保留其
历史版本用途，但不能作为新 v0.3 的覆盖证明。

## 建议修复顺序

1. 修 F01，建立只用 fixture 的公共入口完整链路及恢复用例。
2. 修 F02/F08，落实可比较的①／②观察交付、材料和修正机会。
3. 修 F03/F04/F09，补齐候选可见、逐 finding 处置、仲裁恢复与接受终态。
4. 修 F05/F06/F07，将新义务与依赖/未知消费接到原运行时，补旧根因的新版回归。
5. 补来源/介入点/修订映射和 D 接受入口，再准备五条件材料；工程验证完成后才开真实小批。

Gate Probes：报告承担发现实现与设计差距的责任；证据是固定 HEAD 的源代码和用例引用，
不是运行结果。下一步需要根因修复和对应行为验证，不能直接用现在的①／②跑分来评价 Jev 价值。
