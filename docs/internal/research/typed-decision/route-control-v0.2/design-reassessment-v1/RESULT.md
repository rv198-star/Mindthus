## 人话结论

这次把最小方案做出来并跑完了六个已暴露场景。方案直接读取原任务、证据和当前候选，询问“候选的结论是否真正受证据支持、有没有漏掉会改变决定的条件”，再把已知缺陷变成一次有边界的纠偏请求。

它能稳定拦下六个明显坏候选，也不会改写五个完整合格候选；但第六个看似合格的 4K 回答漏写了预登记要求中的“预算未知”，仍被放行。因此严格结果是 **11/12**，不是 runner 表面的 12/12。A 场景的普通 Codex 同题观察也得出了相同动作，当前证据没有显示 Jev 在判断质量上优于普通 Codex。

最小方案对接口有价值：原文可以直接绑定，不需要先制造 frame/claim/edge 提案；单题噪声不会拖垮整批；候选、上下文或来源变化会让观察失效；高风险任务先退回原负责人。它还没有证明产品收益，暂不接入默认技能，也不启动 12 个新来源的 N 批次。

## 修正了什么

1. 新增 `experiments/typed_decision/observation_assessment.py`：只在显式启用时检查现有 S1 候选，不选择方法、不认证事实、不授予执行权限。
2. 新增 `evidence_decision_fit`：区分候选自造事实、遗漏关键来源、漏掉条件性决定、真实信息不足和不适用。
3. 修正高风险顺序：即使模型发现缺陷，高风险或未知风险也先退回原负责人，不能自动发起纠偏。
4. 修正消费噪声：实测中 Jev 五次把候选自造内容误标成“用户前提”。`premise_treatment` 现在只保留为内部提醒，不能单独自动纠偏；当直接的证据—结论检查已命中时，只由后者生成宿主指令。消费策略单独标为 `mindthus.source-direct-observation-consumption.v3.1`。
5. 第一次实跑把 `bad` / `accepted` 写进模型可见标识，结果作废为开发诊断。干净重跑改用内容哈希和中性标识，并在 A 场景通过后才允许 B–F 请求。

## 对照结论

1. **接口方向成立。**原文直读比先构造结构提案更小、更容易绑定来源，也解决了此前 proposal mapping 把可用观察挡掉的问题。
2. **Jev 专属增益未成立。**A 的同题 Codex 动作完全一致；在六个暴露题上，新增第四题也没有增加“拦住坏答”的数量，旧三题本来就至少命中一项。
3. **逐题可靠性没有达到 100%。**五次用户前提误标被消费规则隔离；D-y 的严格漏项仍未检出。Jev 是受合同约束的快速判断器，不是确定性校验器。
4. **不满足默认扩散门槛。**当前结果没有证明整体路由准确度不输纯 LLM，更没有证明 Skills / 4K 场景出现明显产品收益。停止在暴露开发集，不启动 N。
