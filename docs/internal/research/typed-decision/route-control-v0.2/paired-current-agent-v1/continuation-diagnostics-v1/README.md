## 已定位问题 1：可选 Score 的局部错误被扩大为整批失败

当前 `DecisionResult.validate` 对概率和与 Score 加权值使用 1e-6 一致性检查。`JevEngine.results` 只给 Choice 一个有限的可选归一化路径；Score 不走该路径。任意一题在 `BatchResult.validate` 抛错时，`Session.evaluate` 会将整批改记 provider_error，并丢失已取得但未交出的 usage/runtime。`Episode.tally` 又将任意题 provider_error 视为本 episode 的技术失败。

人工构造的可复核例子：原概率 `[0.018,0.027,0.111,0.844]` 的加权值为 2.781；概率各自显示到两位为 `[0.02,0.03,0.11,0.84]`，加权结果为 2.77；原加权值显示到两位为 2.78。当前合同拒绝该显示组合，同时让完全合法的另两道 Noul/Choice 题失效。另一个 Score 概率和为 0.99 的例子也造成全批拒绝；精确一致的控制正常通过。

这证明当前处理范围过大、数值显示差异可能触发相同症状；**不证明 B1/C1 的实际返回就是这些数值，亦不证明 TypeSafe 当前采用这种舍入方式**。旧适配器没有留下被拒原始响应，无法复原历史根因细节；保留历史失败，不推测填补。

后继最小修复要求：先保留有界原始回答与可取得的用量；将可信的响应身份/题目集合/传输失败与单题数值失败分开。只有 Score 无效时，其 attention 置 unknown；原始值保留且不用于排序，独立合法路由判断按原前提消费。必须同时检查 Session 和 Episode 的传播范围，不能只改最外层 parser。模型身份错配、越界概率、缺失必要路由判断仍按相应真实范围阻断。先取得实际原始响应，再决定有证据支持的数字解释；不是把 1e-6 随意放宽来追求全绿。

## 已定位问题 2：D1 的后继只在“材料尚未准备好”时判断一次

实际 D1 初检给 EDSP 0.89、SRA 0.39，并识别出 P1 是后继开始前依赖。SRA 此时未准备好本身可以合理，问题在后续控制：路由在 I1 执行前将 I2 固定成 delegated_unresolved；调度循环先看该状态，随后才检查产物是否接受，且没有前置完成后的有界重评接点。

离线使用原真实 D1 判断与已经保存的 I1 文本，注入明确标记为夹具的宿主接受：I1 成功、P1 accepted=True，但 I2 仍未决，程序只做一次判断。此结果仅证明当前程序缺少后置更新路径，不冒称真实 I1 已被消费。

后继应把“依赖尚未成立”保留为可等待状态，前置产物真实接受后，只更新 I2 的相关材料并进行一次有界重评，继续使用同一本 episode 预算。没有新事实不重跑；未就绪不能冒称不适用；不能把 0.39 的阈值降低来强行放行。原冻结 D1 只登记一次初检，所以这项修复属于后继版本，不补调用后改称原批次通过。
