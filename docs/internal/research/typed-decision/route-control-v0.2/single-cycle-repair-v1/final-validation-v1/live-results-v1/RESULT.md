## 2. 4K 具体在哪一步失败

组织器已经写出本次需要区分“解决楼主的实际使用顾虑”与“消除4K/5K先天差距”，并保留原图缺失边界，候选方法只给出 EDSP。官方返回：

- `COVERAGE.global = covered`（该选项概率0.79）。
- `COVERAGE.i1 = missing`（missing概率0.65）。
- `G03.i1 = judge`；`M02.i1.edsp = 0.42`；角色倾向 support。
- 程序实际终点：`no_current_candidate`，`pending.i1 = candidate_coverage_missing`。

直接阻断不是本轮 Key、网络、Schema 污染或 KeyError；是当前候选覆盖判断的消费规则。没有候选回答，后续定点纠偏也无从发挥。本轮不把该记录改为方法误判准确率，也不通过调整阈值让它放行。

两位独立评阅者均认为：缺原图限制了逐字核实和实测效果确认，但现有转述仍足以支持有条件的回应；空答未完成用户任务。基线明确按楼主可接受使用目标判断，也没有再次把实用价值硬限为买后，同时不把用户“都解决了”当成已验证事实。

| E⓪ | 3 | 0 | 35.781秒 | 121,501 | 2,591 |
| E② | 3 | 2 | 41.613秒 | 133,476 | 4,135 |

E②两次 Jev 合计约0.581秒，但没有减少大模型调用次数，仍为3次；本次质量均达标时，其请求耗时与报告token量反而更高。这里是单次开发观测，非稳定均值或统计显著性结论。

F②更短是因为提前停止且没有交付，不能算同等任务质量下的成本改善。以上耗时为实际请求耗时相加，不等于包含工具调度/间隔的完整墙钟时间；token是客户端报告的累加值，不等于已结算计费token。费用字段均未知，未假定免费，也没有把缓存、审计、设计投入藏进一个虚构的省钱比例。

四次内容评阅成本另列在 summary.json，不混入日常分支业务成本。本轮新增3次JeV业务请求、10次宿主业务调用、4次内容评阅；本A周期累计Jev已用4/8。未重复工程回归或代码审计，未因语义不利重试模型。

## 4. 为什么这次基线仍然能通过

E这次只有第一条用户问题，没有后续范围纠正；默认仅提供真实using-mindthus入口与目录，没有八方法全文预注入。E⓪本轮未读取额外方法正文，首答经过复核后原文保留。F⓪同样原文保留，未额外读取方法正文。

因此，E的两项已知可比性问题在这次运行中确已移除，但基线仍能在当前入口规则下作出合格的首轮判断。这是本次实际观察，不能为制造Jev优势故意削弱基线。它仍是“当前using-mindthus入口＋宿主”，不是没有方法指导的裸模型。

同时，F仍是纠正后的历史快照，原图缺失；E仍没有验证原来助手先答错再被纠正的完整多轮轨迹。不能从两个通过推导“最初所有历史痛点已解决”。本批能回答的是“当前这两个来源窗口，新增Jev控制是否值得”，不能声称证明普遍准确率或泛化能力。
