## 真实回答原文

我基本同意前半句，但不同意“因此它们只是换名炒作”这个结论。

从模型看到的内容来说，Skill 的核心通常确实是 Prompt：规则、步骤、示例和边界最终都要进入上下文，模型才知道怎么做。SOP、Workflow、Agentic 也不会凭空改变模型参数，更不代表模型突然拥有了新的认知能力。若有人把“把提示词放进文件并按需加载”讲成基础智能突破，那就是包装过头。

但工程上的“本质相同”，不等于产品能力没有变化。函数也可以说本质上只是代码，数据库索引本质上只是额外数据结构，可一旦加入明确接口、触发条件、版本管理、权限边界、工具调用、状态持久化、验证与失败恢复，它们就不再等同于一段随手复制的文本。

可以这样区分：

- Prompt：这一次告诉模型怎么做。
- Skill：把一类任务所需的指令、资源、脚本和验收方式封装成可复用、可发现、可按需装载的能力单元。
- Workflow / SOP：规定多步骤任务的顺序、条件、输入输出和检查点。
- Agentic system：让模型在运行时根据环境反馈选择行动，并把工具、状态、权限和停止条件接入闭环。

差异不在名字，而在系统是否真正提供了这些约束。如果一个 Skill 只有一份 Markdown 提示词，没有工具、状态、测试或执行保障，那么称它为“可复用 Prompt 模块”最诚实。若所谓 Workflow 只是要求模型“先 A 再 B 再 C”，它仍是软约束，模型可能跳步。若系统能强制状态迁移、校验产物、限制权限并在失败后恢复，那就出现了提示词之外的实质能力。

所以我的判断是：Skills 的语义核心是提示词工程，工程形态则可能超出提示词工程。真正该批评的不是新术语本身，而是把“组织得更好的提示词”冒充“模型能力跃迁”。判断它是不是炒作，直接问四件事就够了：它新增了什么可验证行为？哪些约束由系统保证而不是靠模型自觉？失败时如何发现和恢复？去掉这个封装后，维护成本与成功率是否明显恶化？答不出来，多半就是包装；答得出来，新名字至少在工程层面有意义。
