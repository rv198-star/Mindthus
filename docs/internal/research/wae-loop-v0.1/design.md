# WAE Loop 机制设计 v0.1：启动定界，按交接障碍局部深入

日期：2026-09-07
议题：#207

源码阅读基线：`1527f32b99c375db9ff73f80812c644686a6576a`。

## 1. 核心与一页主路径（core / mainline）

> 当前负责人在启动时确定的职责与用途范围内，把工作推进到指定承接者可以可靠接手的充分粒度；只有具体交接障碍仍需本层解决时，才局部深入。

“充分粒度”允许多个合理停止点。以达到用途和约束为前提减少无效工作，不要求证明绝对最浅，也不许诺零风险。

```text
启动：复用已有任务和业务 Skill，确定一次交接约定
  ↓
当前产物是否足以支持约定的下游用途？
  ├─ 是：交接当前范围，退出
  └─ 否：指出具体障碍，按已确定边界归属
          ├─ 本层有权解决：做最小充分的设计、取证或能力支持
          │                    ↓
          │             形成实际成果，检查受影响的交接边界
          │                    └────────── 回到判断
          ├─ 需要他方事实/决定/能力：提出准确输入或转交需求，暂停
          └─ 没有有效可行下一步或预算耗尽：停止，保留未完成范围
```

循环检查“这一次能否交接”，不反复询问“我是谁、下层是谁、谁有权决定什么”。它是自适应委派深度，不是通用审稿、打分到通过或遍历每一层代码。

## 2. 启动约定：四个问题确认一次（mainline）

| 启动问题 | 要固定的内容 |
| --- | --- |
| 当前 Owner 负责决定什么？ | 当前负责人能作出的选择、需保真的来源和职责范围 |
| 下游 Owner 负责决定什么？ | 指定承接者、合法设计自由、所需能力与实际可见输入 |
| 什么留给下层会构成越权发明？ | 必须由本层或被明确保留的其他主体决定的结果性选择；事实不能由猜测补齐 |
| 这次交接服务什么用途？ | 下层要完成的动作/决策，以及达到什么结果即算足够 |

这是短的“交接约定”，可直接引用已有任务书、阶段合同、品牌/数据约束或知识用途描述，不要求另写四份材料，也不要求用户手工填写 Schema。

已有明确说明直接采用；低风险且不改变权限的解释由 Agent 可见地整理。只有缺口会改变目标、授权、承诺、不可接受风险或验收，才集中询问缺失部分。用户目标、外层安全/权限限制和业务职责冲突时显式暴露冲突，推断不创造授权。

某个不重要的细节未知不阻断全部任务。约定可以保留范围外或允许下层决定的未知；阻塞必要动作的未知不能靠标为“以后再说”变成可交接。

预算、风险底线、来源版本、输出方式复用外围任务设置。模型名称或“专家”角色不能单独证明承接能力；已有相关表现可作依据，能力未知保持未知，不为启动 Loop 先跑一套大基准。

### 约定稳定，但可以有明确变更（boundary）

新增普通 finding、措辞改变、补充一个范围内事实、进入下一细节层，都沿用原约定。

只有用途/范围改变、角色或权限改变、承接者实际配置改变，或新证据证明原职责/来源假设不成立，才更新受影响部分。记录变化原因和授权来源，不重新问完四个问题。影响之外的工作不重开。

源版本改变时标明新的取证边界并检查相关结论，不假定全部证据继续有效，也不自动扩大范围。Loop 自己没有批准权限扩张或预算续期的权力。

## 3. 通用机制与业务知识分别归谁（mainline）

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| WAE Loop 方法 | 组织交接障碍、归属、深入收益和停止的判断步骤 | 提供所有领域共用的“完整字段全集” |
| 业务 Skill / 当前 Owner | 按任务来源判断业务含义、充分性、可接受自由；完成必要设计或取证 | 重造一套候选发现、审批、预算和终审运行系统 |
| 外围 Workflow / 实验驱动器 | 来源/产物绑定、合法动作、预算、记录和确定性检查 | 依据字段数量、深度标签或模型自评分决定业务已充分 |
| Evidence | 约束事实与效果声明，提供反例、正向任务和实际接手结果 | 自动把一次审查意见提升为事实或权限 |

WAE 不是另一个不懂业务却替 Owner 下决定的裁判。执行该 Skill 的 Agent 仍需运用业务材料作判断；业务 Skill 提供职责和用途，WAE 提供可复用的判断纪律。正文中的表格是设计说明，不是要求每个任务逐项输出的表单。

## 4. 循环内的唯一判断：现在能否可靠交接（mainline）

在固定约定下检查：下层若现在执行，会在哪里被迫猜本层事实、替本层作决定，或遇到已有证据支持的能力/验证障碍？

充分性同时需要：

- 约定用途内的代表性正向动作能够说清，激活的关键风险有处理依据；
- 本层必需决定与已确认事实没有实质冲突，剩余选择可合法委派；
- 承接者可见的交接材料足以使用，必要证据、权限和验证条件可获得。

只做对当前工作有结果影响的检查，不枚举全部产品话题、函数、异常或未来用途。没有找到反例不是独立的充分性证明；一次模型说“我懂了”也不是实际接手证明。

### 有效深入理由

一段短说明足够：

> 下层要做什么；现在在哪个结果性选择或事实处可能出错；按启动约定归谁；这次最小工作将解除什么障碍。

例如“不同实现会改变审核批准所对应的记录版本，而批准范围由当前负责人决定”是有效理由。“还有很多细节”“可以更专业”“Reviewer 又想到了建议”本身不是。

真实选择同样改变输出，但处于下层获准自由范围内，不构成必须上收的障碍。审美和表达也可能是关键结果：是否需要本层细化，仍由本轮用途和职责决定，不把非数值目标降为装饰。

## 5. 四个动作与正确后果（mainline / runtime support）

| 动作 | 条件与结果 |
| --- | --- |
| `handoff` | 当前声明范围充分，输出可用交接材料并退出该范围的深化。范围、合法自由、适用限制明确。 |
| `refine` | 有具体障碍，本层有权且有可行最小工作；实际补决定、证据、设计、示例、算法或实现，再检查。 |
| `need_input` | 缺必要事实/权限/其他 Owner 决定或获准的能力支援；说明需要谁提供什么、何时可恢复。上游 Return 使用这一结果，不另建返回引擎。 |
| `stop` | 缺少有价值的下一步、风险不能接受或资源耗尽；保留未完成范围，不伪装成功。 |

探索发现“仍未知”可以有信息价值，但若不能解除阻塞就不自动取得交接资格。机械检查失败先分类：语法、执行器、格式错误交由既有实现修复；只有它暴露新的语义/能力边界问题才重开深化判断。

### 两种合法交接

**机械交接**：语义选择已明确，剩余行为由合同确定，未知输入有明确拒绝/降级。

**Agentic 交接**：本层负责的含义已明确，剩余选择明确属于下层且具备相应权限、能力和验证条件。实现不唯一也可以交接。

“Owner 已经全部做完”可算交付成功，但单独标注，不把空的下层工作算成成功委派，也不忽略上层成本。

## 6. 怎样深入而不失控（guardrail）

### 按障碍和依赖成组，不按固定层数

架构、详细设计、算法、代码只是可用成果形式，不是必须走完的层级。普通模块可先交接，困难核心继续；局部化以真实依赖为界，不限于最新 finding 指向的一行。

新增核心决定若影响已交接范围，标记相关结论需复核，并把调度/重返交给外围流程。Loop 不自行改任务状态，不重开无关分支，也不建立第二个 TPlan。

### 信息增长不等于文章增长

必要深化可以是删掉矛盾分支、用一条正确规则替换多个补丁、补证据入口或画一张必要草图。产物更长、字段更多、触达更深都不是单独的收益信号。

对同一障碍保留简短关联记录，而不是把每个新 finding ID 当成全新问题。同一材料上换个说法不续期开销；真实新反例仍可重开。是否同一语义问题由 Owner 解释，脚本不通过文本相似度替它裁决。

### 预算与审查

进入细分支、换 Reviewer、恢复会话都消耗外围同一任务预算。实验驱动器只对它控制的调用强制计数；未接管的宿主行为不声称已经受控。预算耗尽暂停而不是冻结为成功。

Reviewer 是可选证据来源，不是每轮固定增加的角色。本轮用户要求的多专家属于方案评审，不进入产品默认运行链。候选可以部分接受、全部驳回、按下层自由保留；最终动作来自 Owner 的有依据判断，而不是追求零 finding。

每次实质修改后检查关联语义和交接用途，不必固定新增模型终审；是否需要外部复核由风险和验证缺口决定。不能以节省调用为由跳过已承诺的必要检查。

## 7. 用户描述不完整与未知的处理（boundary）

**进入前的边界未知**：从当前任务、业务合同和用户明确约束整理；必要时只补问影响边界的内容。

**进入后的对象未知**：在固定边界中判断该查、该决定、留给下层，还是请求他方输入。这不是重新定义职责。

例如“这个页面怎么排版”在已授权的实现自由内可由下层决定；“批准是否因修改而失效”按现有职责归属处理；“用户承诺的收入是多少”不能根据目标虚构。

有已授权的低风险可逆默认值可以使用，并披露适用范围；不为避免问用户把事实未知变成默认真相。只有真正阻塞用途的缺口才暂停，避免靠全部 `need_input` 获得虚假的安全表现。

## 8. 最小交接材料与记录（runtime support）

交接正文首先服务接收者：目标/用途、当前必要结论与证据、允许的选择、需要的设计/算法/参考、验收与未决限制。已有材料可引用，但必须对接收者可见且引用可用。无需复制完整推理或所有审计轨迹。

实验只需一份启动约定、版本化产物和追加的短步骤记录：

```text
约定引用 + 当前范围/产物 → 动作 + 具体理由
→ 本次做了什么/取得什么证据 → 累计成本
```

记录结果和可核查理由，不收集私有推理链。生产持久化、恢复、任务/权限状态继续归外围系统，本候选不新建通用 schema 或账本。

## 9. 三个场景共用机制，不共用内容清单（example）

| 场景 | 本层负责 | 下层保留的自由 | 必要深化示例 |
| --- | --- | --- | --- |
| F：WFF 阶段交接 | 当前阶段的产品/设计决定及已冻结上游含义 | 下一阶段权限内的设计/实现 | 说清批准对象与修订显示的关系，避免页面展示误认当前草稿已获批准 |
| K：EKRI 知识重建 | 固定来源支持的工程事实、证据、未知边界 | 使用知识作获准的理解、复用或改造判断 | 查到重试副作用与状态落盘顺序，保留失败窗口而非复制整个函数 |
| S：Slidethus 策划交接 | 面向受众的表达目的、立场、必要论证和证据含义 | 在品牌/任务约束内的版式、图形及视觉实现 | 当图示决定论证含义时补图表语义或草图，而非所有页都写坐标和字体 |

F 的 P1→P2、P2→P3 分开，不能合成一个无限权限 Owner。K 区分“实际是什么”与“可以怎样改”。S 的创意表达允许多解，不能伪造数据、擅自改变受众/目的，或把正确内容的单纯美化当成 WAE 必需深化。

三个场景均为待构建的代表性夹具，不是报告它们的生产系统已具有本机制。具体启动约定、范围、多解验收和极端变化见评审包。

## 10. 与现有 Mindthus 的接口边界（boundary）

现有 Ownership Closure 提供追踪语义选择的基础，本候选增加显式深度选择及 Agentic 委派出口；不是声明所有现有 WAE 都只有单层判断。

- WAE 负责本轮应亲自做到哪里；业务 Owner 负责具体含义。
- TPlan 负责长任务生命周期、恢复与 mutation；Loop 不复制。
- SRA 可在多个有效深入方向竞争预算时补位，不强制每轮调用。
- TVG 可在已清楚的文本价值目标下强化产物；“策划还能更动人”不自动属于交接障碍。
- WFF、EKRI、Slidethus 分别维护其生产控制流程。研究夹具不连生产仓库执行，不修改它们的真相或发布产物。

## 11. 阶段与退出门槛（runtime support）

**当前交付**：本设计和三场景评审任务书；下一步先评方案，再构造实验。

1. 三场景分角色评审：用明确反例检验启动约定、深入与退出、多解边界及成本。候选结论不当成真实用户反馈。
2. 汇总并只修已成立的共性问题；保留场景差异，不把九个角色的偏好全部升级成规则。
3. 冻结夹具、允许结果和实验协议，完成驱动器零模型调用自测。
4. 有界 A/B/C 实模试验；独立接收者实际工作是主验收。
5. 重复性、成对变体与净价值成立后，再评审正式 Skill 推广。

方案评审通过只表示值得实验。代码/夹具自测通过只证明实验设施。不能据此宣称 Loop 稳定、有用或能避免16小时过载。

## 12. 本轮已收口与仍待评审事项

已按用户要求写入方案：四项边界启动确认；循环按既有边界归属而不重新划权；WAE通用逻辑与业务充分性结合；增加Slidethus主场景；默认无多专家运行时。

待评审重点：边界暂缺时是否会过度询问；风险模糊时是否既不冒进也不全部阻断；能力不足与语义不足是否能区分；局部改动跨模块依赖是否会漏检；策划充分性是否能多解验收；实验是否能够把显式Loop的价值与更好指令/更多计算区分。

本轮仅做作者的一致性整理，**没有执行三场景多专家评审，没有驱动器、oracle或实模结果**。
