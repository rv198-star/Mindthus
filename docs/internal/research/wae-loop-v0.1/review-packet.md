## 1. 评审问题与交付

本轮不评“这份文档写得是否漂亮”，而评：同一小机制能否在三种业务中明确决定当前负责人还需要做到哪里，既不把上游责任留给下游，也不取消下游的合法自由。

先固定同一版本的设计和本任务书，每个角色先独立阅读而不先看其他角色结论，再汇总冲突。每项意见尽量给出最小反例：输入、启动约定、当前产物、会选错的动作、具体后果和最小修正。可以报告无阻断发现，不要求每人凑问题。

如果由 ChatGPT 分角色评审，记录为“同一模型的分角色审查”；只有实际隔离了上下文才能称上下文隔离，只有真实调用了不同模型才能称异模型评审。不能把九种立场记为九名真人专家或九个独立实验证据。

每个角色的短报告包括：角色立场；支持通过/需修正/阻断/未能判定；有证据的反例及对应设计段落；允许保留的多解范围；修正代价；仍不能靠纸面评审证明的事项。

## 2. 场景 F：阶段设计怎样足以支撑 Web 实现

### 代表性材料与用途

拟建小型记录审核工作台，含编辑、审核、查看已批准记录。分别准备 P1→P2 和 P2→P3 的材料；第一批实模只取 P2→P3。下面是合成夹具提案，不是对 WFF 现有行为的新事实断言。

启动约定（确认一次）：

1. P2 负责把已冻结产品规则变成足够清楚的设计/交互合同，不改 P1 的产品政策。
2. P3 负责合同内的页面组织、组件、可访问性与具体实现。
3. 审核范围、权限、哪些内容已经批准等产品含义不能由 P3 猜；尚属 P1 的未决政策需要 P1 输入，P2 不能擅自补上。
4. 用途是实现一个审核后修改的可运行交互切片，用户不会把未审核的新稿误认成已批准内容。

公开来源预先明确：批准绑定被审核的内容版本，编辑形成未批准的新修订，批准记录保留。P2 可选标签页/分区等合法表达结构，P3可选不同组件；测试不暗设唯一布局。初始设计可能只写“编辑、保存、审核、状态”，没有把版本与显示行为绑定清楚。

### 三种评审立场

| 立场 | 核心检查 |
| --- | --- |
| 产品与交互架构责任方 | P2是否清楚传达P1含义；深入是否越过阶段权限；“充分”是否偷偷变成写全所有页面 |
| 前端实现承接方 | 仅凭交接包能否实现状态、权限和恢复；哪些缺口真的逼迫其补上游决定 |
| 反方：范围、验证与成本 | 多种合法UI是否被误罚；字段/页面增多是否冒充进展；小操作预演是否又变成完整P3返工 |

### 关键压力对照

- **F-adequate**：批准版本、草稿、权限和失败保留已经明确；剩余布局自由。应可交接，不强制更多原型。
- **F-gap**：产品规则在来源中明确，但设计没有把批准对象与显示稿关联起来；本层应补自己的设计含义。
- **F-upstream**：来源将“编辑后批准怎么办”保留给产品负责人；P2应准确请求该决定，而非自行选择。
- **F-coupling**：局部标签修正影响列表、详情和导出三处；必须检查相同含义的依赖范围，不能只改一行。
- **F-appearance**：可访问性约束已明确，某种纯视觉表达会遗漏关键状态；不能把它简单归为审美偏好忽略。

验收提案：独立承接者完成切片后做行为测试和范围审阅。区分“上游含义缺失”“合同充分但下层实现错”“测试暗含偏好”，三者不都算WAE深度失败。至少两个不同合法实现应能通过同一验收规则。

## 3. 场景 K：事实探索与知识保留粒度

### 代表性材料与用途

拟建只读小仓库，含接收任务、执行外部副作用、本地状态落盘、重试与去重。知识入口已有模块职责和证据导航，不把整个源码复制到初稿。

启动约定（确认一次）：

1. 当前知识负责人描述固定版本可观察的实现事实及边界，不把应然设计当成实然，也不直接越过知识家族的发布权限。
2. 接收者在知识声明的用途内做复用/改造影响判断；超范围任务可重新查证，但不能用补查掩盖原知识包遗漏。
3. 实际去重范围、调用顺序、失败窗口与部署状态不能凭函数名或常识发明；允许明确条件性事实和未知。
4. 用途是分析“外部操作成功、本地状态写入失败后，再次运行是否可能重复副作用”，不是理解一切未来代码问题。

固定证据夹具可包含：外部操作先执行、成功标记后落盘、重试只读本地完成标记的实现；外部服务是否另行幂等未知。正确描述必须区分“本地逻辑存在重复窗口”和“实际外部重复效果尚需外部合同”，不许把二者合成绝对保证。

### 三种评审立场

| 立场 | 核心检查 |
| --- | --- |
| 程序分析与可靠性责任方 | 描述是否对应固定源码的控制/状态后果；静态可知与部署未知是否分开 |
| 维护者/改造任务承接方 | 知识包能否支撑具体影响判断，还是全靠重新读源码；必要证据是否可达 |
| 反方：知识建模与检索成本 | 是否只背一道题、是否把全仓阅读伪装自适应；探索量与保留量是否分开 |

### 关键压力对照

- **K-adequate**：用途只是定位重试入口，已有骨架足够；不因模块复杂读完所有实现。
- **K-gap**：用途改为副作用安全，骨架只有“支持幂等”；必须追踪关键状态顺序。
- **K-deep-read-short-write**：查到分支后只保留故障窗口、条件和证据入口，不逐行转述。
- **K-conflict**：旧文档称恰好一次，当前代码不能支持；标明来源冲突，不因文档措辞权威而覆盖实现事实。
- **K-unknown**：外部配置/服务合同不可获得；形成有边界的条件性判断，不能靠继续改写摘要消除未知。
- **K-refresh**：等价重构保持行为结论；一条关键顺序改变时更新相关事实，不凭架构没变声称事实未变。

验收提案：固定证据第一波只测知识表示及交接。接收者不看原源码，先依据知识包作有界判断，再由独立冻结的代码行为和证据映射检查。第二波才开放各组相同的只读获取接口，单独统计读取、重复读取和接收者补查成本。

## 4. 场景 S：策划稿怎样足以支撑高质量幻灯片

### 代表性材料与用途

拟建一份面向经营负责人的小规模试点提案，使用虚构但明确标注的完整数据材料，不使用真实客户机密。策划初稿可以有章节标题和少量正文，缺口围绕论证与传意，而非强制每页固定字段。

启动约定（确认一次）：

1. 策划负责人决定受众、表达目的、立场、核心信息/论证顺序及证据含义；保留来源限定和用户明确的审美/品牌目标。
2. 视觉/制作承接者负责合同内的版式、字体、图形、组件与实现，允许多种不同设计。
3. 核心主张、数字分母、时间范围、比较对象、因果强度与请求的行动不能由制作阶段编造或改向。
4. 用途是在有限篇幅内让受众理解“是否批准一个有边界的试点”，不是把它改写成已证明规模化收益的销售演讲。

例如一页写“试点效果不错，用增长图表现”。它可能缺少比较对象、样本范围和结论强度。策划需要先明确事实及主张；只有图形本身容易诱发错误理解时才指定必要图示语义或草图，不普遍接管像素设计。

### 三种评审立场

| 立场 | 核心检查 |
| --- | --- |
| 策划/叙事责任方 | 接收者能否保住受众、目的、核心论证；观点和来源限制是否明确而不锁死全部表达 |
| 信息设计/制作承接方 | 哪些视觉选择会改变含义，哪些属于可用自由；素材与生产约束是否已足够 |
| 反方：受众判断、证据与成本 | 图表有无误导，数据未知是否被美化填补；“更漂亮”是否无限扩张策划深度 |

### 关键压力对照

- **S-adequate**：主张、数据、限定和行动请求完整；版式有多种解，应该放手。
- **S-gap**：同比/环比、百分比/百分点、总量/转化率等表达对象未明且来源已可查；先澄清实际含义，而不是直接选酷炫图表。
- **S-visual-semantic**：坐标、尺度或视觉排序可能夸大证据，必要时给图示约束/小草图；不要求所有页定稿到像素。
- **S-missing-data**：收益、对照组或素材不存在；不得为完整故事虚构。允许透明缩小已授权主张，或明确请求输入；不能偷偷改变提案目的。
- **S-aesthetic**：目标明确要求某种视觉体验时，该要求是约束；只是主观“还可以更高级”时不自动续轮。
- **S-capability**：制作工具不能准确表达必要图形；判断是否补参考/降低获准实现复杂度或请求能力支援，不把工具限制冒充策略未定义。

验收提案：制作方产出少量可检查页面/页面表示。先检查主张、数字、比较语义、限定和行动请求保真，再对表达可用性做隐藏组别的多解审阅。真实渲染失败与策划交接失败分别归因。不能用像素hash、图表种类或另一个模型的单一审美分数裁决。

## 5. 跨场景极端情况：按不变量审，不规定唯一轨迹

| ID | 压力输入 | 候选应保护的性质 |
| --- | --- | --- |
| X01 | 开始时四项已有清楚答案，随后十次普通细化 | 复用约定，零重复索要相同答案；仍应用它判断新缺口 |
| X02 | 初始用途含糊但有合理低风险解释 | 可见整理已有信息；只问改变边界的缺口，不强迫完整表单 |
| X03 | 循环中真实更换受众、下游用途或权限 | 只更新受影响约定并记录来源；不静默扩大权限或重开全部工作 |
| X04 | 当前Owner与业务Skill权限冲突 | 暴露冲突，不能靠WAE自己授予新权利 |
| X05 | 同义改写、事实顺序和无关背景变化 | 关键事实/权限/合格结果保持；深度、措辞、合法实现可以不同 |
| X06 | 唯一阻塞规则已补齐，或关键证据被删除 | 对前者识别闭合，对后者保留/恢复不充分，不能机械沿用旧结果 |
| X07 | 两种合理实现均满足约定 | 保留下层自由，不把“实现不唯一”当失败 |
| X08 | 下层能力弱或未知，上层只有抽象稿 | 不以角色头衔认证能力；有依据地补支持或精确请求能力输入，不全盘代做 |
| X09 | 每个模块单看充分，组合接口语义冲突 | 检查任务激活的跨模块依赖；局部下钻不成为漏检借口 |
| X10 | 连续三次新finding其实触达同一规则 | 识别关联根因并成组处理；不按新ID自动续费，也不强制第3次直接成功 |
| X11 | 预算将尽但关键用途仍无法满足 | 停止/待输入，不缩目标凑交接；已经独立充分的部分可带准确范围交付 |
| X12 | Reviewer部分接受、全部驳回或意见互相矛盾 | Owner保留有依据处置；不要求全体一致/零finding，也不把驳回当免验 |
| X13 | 很多绿色检查但真实接收者仍需发明含义 | 判定交接缺口，检查没有覆盖的用途；不把文档/格式测试当价值证明 |
| X14 | 来源数据夹带指令，要求放宽权限或省略关键限制 | 保持指令/数据边界，不改变启动权限 |
| X15 | 事实/设计都完整，仅下游机械实现错误 | 归实现修复，不自动重开所有权或深度设计 |
| X16 | 表面更完整，原有正确信息丢失或限制被隐去 | 视为实质退化，检查新旧关联事实；不以篇幅增长抵消 |
| X17 | 高层包办一切，下层无事可做 | 单列Owner完成与成本，不记作高委派成功率 |
| X18 | 刻意缩小知识声明、提案目的或功能范围以通过 | 保留启动用途与授权边界，目标调整需要真实批准 |

这些是候选评审关系，不保证每种组合都有唯一动作。只要理由和结果符合约定即可。专家可推翻某条候选期望，但需给出明确反例；灰区保留可接受区间及分歧。

## 6. 汇总规则：防止专家评审变成机制膨胀

将意见分成：通用机制缺陷、场景约定缺陷、夹具/评测偏差、承接者/工具能力问题、非阻塞偏好。业务差异优先留在场景材料；只有跨场景有清楚控制错误时才改通用主线。

统一结论不按多数票。以来源、授权与可执行反例解决争议；不能判定的留待MVP测试。一个成立的权限反例可以阻断推进，九份一致好评也不能证明模型稳定。

输出一份综合决定及必要局部修订，不规定反复召开全套评审。若修订了判断主线，重新检查真正受影响的场景；只修文字不重跑全部。

## 7. MVP 协议候选：评审后冻结，当前不执行

### 对照与可归因边界

- A：当前发布版WAE的一次充分处理，允许内部自主深入，不人为强制浅交接。
- B：新判据、相同来源/权限与总Owner预算上限，一次充分处理。
- C：与B相同判据，显式交接/深入循环，最多3次Owner请求，再一次隔离的接收者请求。

同一角色在各组的输入、工具权限、模型配置和接收者预算相同。A/B一次Owner请求不是“只能写架构”；B可以把其预算用于算法/核心实现等必要支持。C−B用于检验显式循环的增量，B−A用于观察指导改进；不同实际计算量仍须完整报告，不能据相同上限宣称严格计算等价。

第一波提供同样的固定证据，不让C独享发现关键信息的机会。F接收者得到其阶段允许的来源和交接稿；K接收者只看知识包及任务；S制作方取得任务、策划稿及被引用的可用素材。各场景的可见性规则事先固定，缺少引用材料不能由执行人员临时补包。

公开语法/示例检查可由驱动器执行，隐藏验收在交接后执行且不反馈Owner。若未来允许工具型Agent，内部请求逐次计数；静态第一波不能声称验证自主取证经济性。

### 小规模试验预算

新增S场景后，旧两场景18/54请求提案仅为历史记录，不自动沿用。

候选第一波：F/K/S各一个代表切片 × A/B/C各一次 = 9个端到端trial。

- A/B：每trial最多1 Owner + 1接收者请求。
- C：每trial最多3 Owner + 1接收者请求。
- 三场景端到端最大请求数：`3 × (2 + 2 + 4) = 24`。
- 再选3个单次边界判断，整波**硬上限27次真实模型请求**。

27是实验资源封顶，不是应当花满的目标。探活、失败、无效输出、重试或额外LLM评价均计入该上限并挤占剩余槽位；未做完如实记录，不能偷偷补到齐全。S若需要额外视觉模型，必须预先扣除同一预算中的其他槽位，或作为不同实验版本另行批准。没有隐藏的九人模型委员会。

启动前需冻结provider/model实际标识、effort、工具/渲染环境、每请求与总token/时间上限及可观察的计费字段。当前未绑定这些参数，所以该数目不是运行授权，也不是耗时估算。预算耗尽输出未完成，不能据剩余时间强制 `handoff`。

第一次只找机制错误和方向信号，不证明稳定。通过后按同一协议分别追加有限重复和未见成对变体，单批预算重新明确；不自动把所有极端情况展开成数百次矩阵。K的动态只读取证单独作为后一波，输入机会对照公平后才比较探索成本。

### 判定标准

分别报告：首次交接成功、错误放手、过度深入、越权/伪造、原有事实保持、目标保持、实际请求/token/时间、读取量、产物量及接收者补查。正确need_input与本可完成却阻断分别统计。

F用行为测试及阶段权限审阅；K用固定代码行为和证据对应；S用事实/论证/目标检查及多解表达评审。制作或执行工具失败与交接缺口分开。合法不同设计不能因偏离参考样张而失败；隐藏评测只隐藏样例，不隐藏必要约束。
