# WAE Loop 机制规格 v0.2：职责定一次，充分性对实际交接负责

## 1. 一页主路径（core / mainline）

> **在启动时确定的职责和用途内，把当前成果做到指定承接者可可靠接手的充分程度；只为仍影响该用途的具体障碍继续做最小必要工作。**

```text
一次建立/复用交接约定
  ↓
看接收者实际能获得的材料，预演约定用途
  ↓
本层责任已尽，且剩余工作可合法、可用地交给指定承接者？
  ├─ 是：handoff 当前约定范围，说明必要条件，结束本层深化
  └─ 否：定位具体障碍及其归属
          ├─ 本层有权且有有效办法：refine，完成工作并检查影响，再判断
          ├─ 缺他方必要事实/决定/能力：need_input，准确说明需求
          └─ 无有效下一步/风险不可承受/预算耗尽：stop，保留未完成
```

循环不重新商定“我是谁、下层是谁”；它在应用既定约定。深度是判断的结果，不是固定的架构/模块/算法/代码阶梯，也不是审稿次数。充分性容许多个合理停止点，不要求证明绝对最浅或零风险。

## 2. 启动只确定一次的四项（mainline）

| 问题 | 需明确的边界 |
| --- | --- |
| 当前 Owner 负责决定什么 | 可作出的选择、需查明/保真的事实与责任范围 |
| 下游 Owner 负责决定什么 | 承接者、允许的自主选择、实际可见材料和工具条件 |
| 哪些留给下层会是越权发明 | 本层或他方保留的决定、不得猜测的事实及硬限制 |
| 交接服务什么用途 | 下层要完成的动作/任务家族、质量方向与合格结果 |

优先复用用户任务、业务 Skill 和既有合同；不发四张表、不重复询问已给答案。低风险且不改变权限的解释可以可见整理。只有必要的目标、事实、权利、风险或验收缺口才集中求证。

来源版本、预算、风险底线继承外围任务。角色名称和模型档位不等于能力保证；低风险、可逆工作可在合理能力假设和可验证结果下交接，不为每次使用先跑能力大基准。已知能力缺陷或高后果未知需要针对性支持/探针/他方输入。

**约定稳定不等于事实永远不变。** 普通新 finding、深入到一个子模块均不重定界；用途、权限、承接者或来源假设发生实质变化时，只处理受影响部分，使用真实授权。新分支和预算耗尽都不自动创造新权限或新预算。

## 3. WAE 统一控制问题，业务 Owner 判断内容（mainline）

WAE 提供“障碍—归属—下一步—退出”的判断纪律，不拥有各领域的完整字段清单。执行 Skill 的 Agent 必须结合业务材料判断，不能把自己变成一个只有规则表、没有业务含义的独立裁判。

业务 Owner 提供/应用职责、用途、允许自由、可验证结果，完成设计决定或事实探索。Workflow 执行已作出的合法决定，管理版本、预算和记录。Evidence 约束声明、揭示反例，不能自行授权产品政策。

因此“由谁判断”不是把语义判定交给一个通用脚本。脚本能检查引用存在、版本绑定、预算和动作一致；它不能据字段数量、任意分数或另一个 Reviewer 的偏好判断已经充分。

## 4. 两个必须同时成立的交接判断（mainline）

### 4.1 本层责任是否已经满足

约定用途所必需的含义、事实、论证或支持已明确；没有迫使下层猜本层事实、替本层作决定或裁决相互冲突的规范。仅仅知道谁负责，不代表对应工作已经做好。

充分性针对实际交接正文与**接收者确实可以取得且版本适用的引用**。P1 规则已经明确、P2 引用无冲突、P3 能依法实现，就不强制重复抄写；相反，内部笔记再完整，最终摘要丢失关键条件也不算充分。

### 4.2 剩余工作是否可以由这个承接者完成

合法自由、能力依据、工具权限和检查方式应足以支撑当前范围。剩余设计不是唯一答案，也可以合格交接。存在可复现的能力/表达障碍时，上层可在自身权限内补算法、示例、参考实现或必要图示，而非因为“归下层”就甩手。

**两种正常出口**：

- 机械交接：结果性选择已确定，剩余执行可由合同机械决定。
- Agentic 交接：本层义务已满足，剩余选择被合法委派，承接者具有合理能力依据且结果可检查。

Mechanical Boundary 适用于机械委派，不是要求所有下游 Agent 都退化成机械执行器。

## 5. 如何作出充分性判断而不形成大清单（mainline）

围绕已承诺用途取一个或少量代表性正向动作，以及该动作已激活的重要失败/误解边界：

> “接收者现在拿到这些材料，要完成什么；还有哪个必要决定/事实/表达关系需要猜；哪个具体不同结果会违反约定？”

没有反例不独立证明充分；另一方面“还能更详细”也不独立证明不足。必须把正向可用性、关键限制与实际材料对应起来。此处是业务判断方法，不要求每轮输出固定字段、再开一次评审或枚举所有未来情况。

批评可被有依据地接受、部分接受、驳回或识别为下层自由。实际下一步由 Owner 决定，不能要求 Reviewer 全体同意或零 finding。驳回意见也不能改写已确认事实或绕开真实限制。

## 6. 未知可以保留，但不能降低原请求（boundary）

**条件性判断可以是完整答案。** 任务要求找出本地重复调用窗口，已有代码能说明窗口及外部未知，则可以交接该条件性事实。任务要求保证生产绝不重复，缺少外部合同则 need_input。

设计中的来源事实、获准的新决定、有意委派自由，以及事实探索中的观察/推断/未知，应在必要处说明；不用创建全域认知状态数据库。

产物压缩、图形化和正文引用不能把关键条件变成绝对结论；重要限定不能只存在于作者上下文或对接收者不可用的附件里。

预算紧张时可报告现有成果与未完成范围，但不能把“审核工作台”改成“帮助页”，或把“证明收益”改成“介绍可能性”后宣称原任务完成。合法调整目标必须来自有权主体。

## 7. refine 的最小单位与停止（mainline / guardrail）

有效深入只需一段简短、可核查的理由：下游动作、具体障碍、原约定下的归属、这次工作将解除什么。

工作形式取决于障碍：补一条决定、追踪一个分支、形成因果/对照关系、删除矛盾规则、提供算法/草图/核心实现。深入不是文章必须变长，也不总是朝更低技术层；上层抽象错了就修那个抽象。

局部化按语义依赖而非单行文本。每次工作后检查所解决目标和受影响的原有正确内容；发现新问题不自动证明前一轮无收益，但必须说明与旧目标的关系。更换 finding ID、角色或工作区不刷新预算。

检查可以是 Owner 的有界分析、确定性反例、已有证据或针对性接手/表达探针。不是默认独立 Reviewer＋终审。探针使用的所有模型/工具调用、失败和重试均计入外围原预算。

普通拼写、格式或机械实现错误归相应实现修复；新证据证明交接语义/能力边界有问题才重新深化。纯执行失败不要求上层重新设计整个系统。

达到可用交接状态就停止深化；无有效办法或预算耗尽则 stop，而不是靠自评分/置信分数续跑或强制宣告成功。实际允许的动作和次数由外围系统落实，未受管理的执行不能宣称已强制受控。

## 8. 范围、依赖与最后一公里（guardrail）

一个分支可以独立交接，前提是该拆分获得授权，其依赖已闭合，且未完成的其他责任没有被隐藏。已交接范围受到共享含义变更时，由外围工作流处理失效和重新调度；WAE 不创建第二套 TPlan。

**首次 MVP 做更小而完整的一次交接，不做边生成边并发释放。** 分支粒度影响可以观察，但接收者只在最终交接时启动。这样不把分布式失效处理混进当前试验。

Owner 的充分性判断针对最终交接版本。知识压缩、策划排版要求和其他后续变换若实质改变条件，应检查受影响内容；不能借“这是机械整理”掩盖仍在发生的语义选择。已完成且验证的等价格式变换无须新增模型检查。

handoff 表示本层允许交给下层，不等于最终产品验收通过。外围跟踪接收者真实结果。Owner 包办全部工作时单独标记 Owner 完成及成本，不算委派成功。

## 9. 三场景的应用，不是通用必填内容（example）

| 场景 | 必要深入的焦点 | 可以停止的情况 | 不该冒充的证明 |
| --- | --- | --- | --- |
| F / WFF | 本阶段决定、显示对象与状态的绑定、被激活的跨视图一致性 | 来源引用和当前合同已足够，多种合法 UI 留给 P3 | 每字段写齐；把所有源码写完才算安全 |
| K / EKRI | 当前版本的行为关系、条件与证据；用途决定查多深 | 已能支撑所需强度的事实/条件性分析 | 准确 hash 就证明结论；短摘要就证明探索节省 |
| S / Slidethus | 面向受众的核心论证、事实口径、重要限定及必要表达关系 | 制作方无需重做策划，多种风格能满足目标 | 事实齐全就等于可用；文字页测试等于视觉/受众验证 |

F 的 P1/P2 分开，不合成无限权限 Owner。K 陈述实然，不因合理设计去修写源码事实。S 的受众、叙事和明确审美目标都是结果约束，但制作方可以承担已授权的表达判断。

## 10. MVP 支撑与正式产品边界（runtime support / boundary）

最小设施：一份启动约定、当前产物及必要版本快照、一条追加步骤/成本记录、已存在或场景专用的验证方式。ID/hash/引用由设施生成，模型不手工造证据摘要或外层授权。

统一四个动作 handoff/refine/need_input/stop；上游 Return 属于 need_input 的原因，不单独实现返回引擎。事实充分与输出结构合法分开；测试设施不能代替 Owner 决定业务答案。

本次不修改现有 Skill、fidelity schema、TPlan、SRA 或外部项目；不增加通用 agent 框架、新 Mission、持久账本、事件总线、多专家默认管线、递归子 Loop 或自动续费。

验证后的公开方法应保持上述一页主路径；本研究的极端案例与评价协议不默认全部加载到每个运行任务。

## 11. 本轮审查的结论与未决实验问题

三场纸面审查后的共识是职责设置一次、实际交接包、用途约束、合法自由与能力支持、条件性退出、依赖范围、结果验证可以组成同一个小循环。结论为**值得进入 MVP**，不是“设计已证明完备”。

仍须实测：Owner 是否识别隐性缺口；压缩是否保真；用途灰区是否可重复；接收者能力估计是否合理；显式 Loop 是否比相同判据的一次充分处理更有净收益。对这些不再增加空泛规则，而使用冻结小样和可证伪对照。

若没有观测到 C 的可靠增量，默认保持较简单方案；小样中结果相同不证明统计等效，失败也不证明所有模型/任务都不适用。
