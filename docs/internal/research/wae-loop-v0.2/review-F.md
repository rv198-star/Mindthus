# 第一场评审：WFF 阶段交接——什么时候是必要深化，什么时候是上收下游职责

日期：2026-09-07。关联：#207 / Draft PR #208。
评审输入：机制规格 v0.1 与 review-packet.md，固定提交 `59d8cbfc81531978a59fc0d63638d593b6499dba`。
方式：本会话 ChatGPT 的三立场对抗式设计审查。不是三名真人、不是隔离模型调用；以下反例为设计推演，未作为 WFF 生产事故或实模结果。

## 1. 各立场的初始主张

**产品/交互架构责任方**：P3 经常把缺少的业务规则自行补全，必须在上游把关键交互含义讲到足够具体。v0.1 的局部深化方向正确。

**前端承接方**：完整性不能按某份文档有没有再写一次判断。P1 规则在可访问来源中明确，我照着实现就不是越权；而把所有实现选择上收，又会使 P2 成为第二个 P3。

**范围与可靠性反方**：两者都可能把自己的便利当作充分性。应展示一个具体输入，在接收者的真实信息和权限下，为什么现在会错误，而不是用“设计更完整”作论据。阶段边界也不能成为上游拒绝补必要工作、下游无限追问的借口。

初判：有条件支持机制，但 v0.1 的充分性检查和夹具描述尚不足以区分真实遗漏、引用式充分与过度规定。

## 2. 争议 F-01：P2 没写的内容，是否必然需要 P2 补写

定位：v0.1 §4、§8；评审包 F-gap。

### 最小反例

启动约定：P1 已确定“批准绑定内容版本；编辑形成未批准的新版本；旧批准保留”。P2 引用准确的 P1 版本，P3 确实能读到；P3 有权选择在两个分区或两个标签页中呈现，不得改变批准语义。P2 没有把上述三句复制到自己的正文。

错误判断：以“P2 中缺批准语义字段”为由继续生成详细设计、原型和状态表。

实际后果：没有消除新的歧义，却增加重复权威和版本漂移面；若基准因此判直接交接失败，它在奖励抄写。

### 交叉质询与裁定

架构立场担忧接收者忽略引用；前端立场指出应检查可见性与冲突，而不是必然重述。裁定采纳后者的最小条件：充分性对**实际交接包及其可读取、版本相符的必要引用**成立。清楚的来源加上合法推导可以充分；接收者漏读归执行问题，链接不可用或规定互相冲突才形成交接障碍。

接受修订 R1：不得以单份产物的字段缺失代替结果性缺口。夹具必须先证明错误风险不是因为刻意禁止接收者使用已授权资料。

反向控制：P2 的视图合同把最新草稿与记录级 approved 布尔值绑定，实际允许把 v8 草稿显示为 v7 的批准。此时即使 P1 引用完整，也存在真实冲突，必须修正，而非要求 P3 自行裁决哪个规范优先。

## 3. 争议 F-02：只要属于 P3，就能放手吗

定位：v0.1 §4、§5 的 Agentic 交接。

### 最小反例

P3 获准实现列表、详情、导出。P2 只说“显示内容和批准状态”，共享数据表示没有保证状态与显示版本对应。单个视图各自可运行；列表展示 v8，批准来自 v7，导出又混用两者。

错误一：所有显示问题都属于 P3，所以立即交接。
错误二：为消除风险，上游规定全部像素、组件和交互实现。

### 裁定

应补的是跨视图的结果约束：“被标为已批准的内容必须对应被批准版本；并列显示草稿时，来源和批准范围可区分。”两个分区、标签页、版本选择器均可合法；具体组件和函数仍归 P3。

接受修订 R2：合法委派与可实施委派分开检查。必要时给关系、示例或参考实现支持，不自动接管下游所有选择。若任务约定允许承接者自行解决某项表示设计，且依据足够，则其方案选择本来就是合法工作，不按上述例子强制归 P2。

阶段约束优先：本研究不授予 P2 改 P1 政策的权力。来源明确保留的产品政策必须返回有权主体；允许当前 Owner 实现算法的架构场景也不能据此为 WFF 改权限。

## 4. 争议 F-03：已交接分支能否独立退出

定位：v0.1 §5“当前范围”、§6“普通模块先交接”。

### 最小反例

列表已经交接；Owner 后来修订详情所依赖的“当前版本”定义。列表仍消费旧定义，但 Owner 只检查详情。反过来，Owner 也可能仅交付无关帮助页，便把整个审核工作台标记 handoff。

裁定：分支退出仅适用于被授权拆分且依赖闭合的范围；承诺的整体用途保持。跨分支规则变化需要标记受影响的旧交接失效并由外围调度处理。WAE 不自行撤销已执行动作，也不复制任务状态机。

接受修订 R3：首次 MVP 不做途中并发部分交接，只对一个完整小切片进行最终交接。独立部分可作为有范围的已有成果保存，不能用其替代整体交付成功。

## 5. 争议 F-04：启动一次会不会把错误假设冻结住

反例：四项已确认；随后发现双方引用了同一政策的不同版本。严格“确认一次”若被理解为永不检查适用性，会让一份过期合同继续决定当前动作；每次发现新字段就问用户四遍则是反方向错误。

裁定：四项职责与用途不重复协商；每轮只核对新增信息是否仍落在原约定内。发现确定的版本冲突，仅处理受影响引用或权限；没有授权不能自行重定政策。使用最新产物不是擅自升级来源版本。

保留并澄清 v0.1 的变更规则，不新增定期复核会议、合同续签或每轮审批。

## 6. 争议 F-05：验收应该检查什么，谁来承担质量判断

至少两个合法 UI 必须能通过。验收检查批准对象与显示内容关系、允许动作及其后果、用户能辨识的状态；不检查唯一组件、文档字段或像素布局。它仍然不能证明所有用户都不会误解。

需要同时有正例“正确完成审核后编辑”和反例“不能把新草稿显示为已批准”，避免只会拒绝所有动作的实现取得满分。

如果最终产物失败，要区分：来源/交接真的不足、引用不可见、接收者违反充分合同、渲染器缺陷、评测加了未公开偏好。不能将全部失败算作 Loop 深度错误，也不能将全部失败推给接收者。

## 7. 本场接受与拒绝的改动

接受：R1 实际交接包充分性；R2 合法自由与承接可行性并存；R3 依赖闭合的范围退出；来源变化只处理真实差异；多解正反例验收。

拒绝：固定 UI 必填清单；每个 finding 自动生成一轮；P2 完成全套页面再交接；每次进入新分支重新确认四项；禁止所有异常上游 Return。

## 8. 纸面复核与实验边界

在修订方案下回查：引用式充分→可交接；批准与显示稿冲突→局部修正；产品政策保留给 P1→准确 need_input；跨视图耦合→检查已激活依赖；两个合法 UI→都允许。

这是规则与反例的设计一致性核对，未运行真实 P1/P2/P3、浏览器或模型。尚需夹具证明接收者只凭冻结材料能执行，并观察初始能力、遗漏和过度深入的实际分布。

本场结论：**修正后可进入夹具设计；不构成 WFF 生产认证。**
