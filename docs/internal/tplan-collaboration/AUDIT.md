# TPlan 协同方案审计记录

日期：2026-11-17。对象：[PROPOSAL.md](PROPOSAL.md) v0.4（主会话目标保持优先，仅 A 启用 TPlan，按任务启用协作能力）。
方式：同一 Agent 在修订方案后，按源码与反例进行设计自审。外部参考来自 Brave 中的 [Gemini 对话](https://gemini.google.com/app/bff360b7ba8da8b9)。

## Core / 审计结论

核心验收是：多会话反馈与中断后，A 的实际判断和行动继续服务用户赋予它的目标、责任与验收标准。委派、收件、版本和恢复机制按此目标组织。

保留 Gemini 的工作焦点隔离、委派看板、检查点批处理和恢复摘要；把自动分流/自动返修的语义判断交回责任 Agent，把来源、版本、幂等、事务与投递恢复写进合同。

按用户的部署要求，默认只有 A 启用 TPlan。此次将原方案中的承接端持久化去重依赖改为 A 侧发送控制及宿主能力合同，新增普通语言回报、歧义补问和零 TPlan 参与者的验收用例。

v0.3 明确使用入口：普通任务默认单会话；出现已授权实际分工时由 A 按需启用协作，后续根据持久记录续接。用户无需另记模式口令。

修订稿可进入完整功能设计评审。落地前仍需冻结具体 API/状态转移、宿主来源与唤醒能力，以及真实失败场景的验证。本文完成的是源码核对与静态反例走查。

## Mainline / 发现及修订

### A01 — P1：把 Guard 内局部写入当作旁路

Gemini Type II 建议将局部反馈写入任务 evidence/validation_findings，同时保持 Mission digest。当前 `schema.md` 的 Guard 摘要覆盖整份 mission.json 和 evidence 边界，公开 writer 在 Guard 开启时关闭写入。增加字段或局部改证据都会触及保护对象。

修订：M4/G3/R1 将传输收件与业务导入分开；已开启 Guard 时只允许宿主保存待导入回执，解除后进入同一事务。来源不明的 peer 消息走原保护路径。对应 T08。

### A02 — P1：让脚本决定局部/全局影响和返修目标

Gemini 要求在 Guard 层做三路语义分类，并在 C 返回 REJECT 时自动生成修复子任务。若问题实际来自错误设计、审查标准冲突或范围新增，机械返修会持续推动错误工作。

修订：M4/M5 由 A 判断影响和修复目标；脚本执行已确定的有限动作。发送者的影响标签是建议。返修有范围、轮次和退出条件，沿用反螺旋规则。对应 T04/T05。

### A03 — P1：用审计 PASS 字段替代合格验收

Gemini 的“来自 C 的 audit_verdict == PASS 证据签名”未确定身份来源、被审成果、合同版本、验收范围和签发方。可导致 h1 的审查结论被应用到 h2，或者转述文本被当成审查者决定。

修订：M5 绑定真实来源、指定审查者、任务/轮次/成果/合同和依据。任务完成与 Mission close 均校验当前采用版本及 required review；H1 受保护场景保留其可信 Host 合同。对应 T03/T11/T13。

### A04 — P1：固定恢复原游标，错过反馈造成的依赖失效

Gemini 要求每次响应结尾输出 `[Resume Anchor -> T2]` 并恢复。若新反馈推翻 T2 的前置假设，固定恢复会让 A 接着完成已经过期的设计。

修订：M6 保存恢复依据，并按最新依赖选择 resume/switch/wait；G4 要求版本与依赖核对。内部摘要按需生成，避免每次向用户重复整段“归位帧”。对应 T09。

### A05 — P1：缺少发送结果未知时的处理合同

原方案有 dispatch/callback，但没有覆盖“发送成功后回应丢失”和“协调者在发送后退出”。重试时新建指令会造成重复执行或审计。

修订：M2/G5/R1 将稳定意图、原生引用和已确认/未决事实纳入一条记录链。发送前持久化意图，未知时查询原执行；关联缺口未解决前暂停同目标再派。v0.2 将重复派工控制集中到 A 及宿主适配层，宿主自主重投的机械去重按真实能力验证，普通 B/C 无持久化接收器依赖。对应 T07/T18。

### A06 — P1：工作焦点之外的任务可能漏收反馈

`_event_is_on_current_path` 对带 task_id 的事件只接受当前活动任务，并排除终态节点；`_collect_feedback_or_blocker_candidates` 将 feedback/user_feedback 合并为 user_feedback 路由候选。协作中的 T1 回执可能在 A 活跃于 T2 时不被关注。对刚验收版本的新风险，也需要明确导入路径。

修订：R2 为所有相关委派收集待处理事件，保持当前业务版本与历史记录的区分；M4 在完成前复查相关待处理输入。最后一轮自审补充 M5：任务已完成而总 Mission 尚未完成时，新合格失败约束当前验收，并通过成功关键修复任务处理，避免依赖当前不支持的 completed 回退。已关闭 Mission 的后续问题进入显式后续处置。对应 T01/T03/T13/T17。

### A07 — P2：把任务状态、角色流水线和焦点混成一套枚举

Gemini 建议 `DRAFTING -> DISPATCHED_TO_B -> SUBMITTED_TO_C -> AUDIT_REJECTED -> AUDIT_PASSED`，并把 active_task 改名。这样把固定三角色和投递/审计事实嵌入通用任务状态，仍未处理 setter 自动改游标的问题。

修订：M3/R1 保留任务树和 active_task_id，委派记录另存执行关系与事实；新增入口明确保持焦点。B/C 作为独立协作会话，开发写入发生在 B 自身授权范围；原只读 SubAgent 合同继续适用于只读审阅载体。对应 T01。

### A08 — P2：把技术假设冻结为不可变架构约束

Gemini 的 North Star 混合了 Mission 与 Architectural Invariants。用户硬约束、暂定设计和待验证依赖的调整权限不同；混合会阻止基于新事实修正设计。

修订：M1 分离用户目标/权限、设计决定和技术假设；在既有授权内修订设计，超出范围才提交用户决定。对应 T04/T05/T09。

### A09 — P2：只在 Step 完成时 flush，反馈可能一直等待

长 Step、持续到来的小消息或即将发生的高影响操作，会使“完成当前节点才处理”失去合适时机。简单的致命/非致命标签也不足以确定紧迫性。

修订：M4 增加可约定的最长处理等待、下一有关副作用前检查、交接/验收前检查；紧迫性由影响与时效判断，相关问题按批处理。对应 T16。

### A10 — P2：所有外部开发统一强制 C 审计

Gemini 按“是否外部开发”决定 mandatory C PASS。低风险委派会承担过多审查，而设计或权限敏感任务即使没有 B，也可能需要独立审查。

修订：M5 将 required review 放进任务验收合同，按风险和交付性质决定。A/B/C 是本次示例，能力支持其他责任配置。对应 T13。

### A11 — P2：用呈现字段存储收件，或把一轮结束当作 Mission 结束

Gemini 把 pending_callbacks 放进 Snapshot，容易形成另一份可写状态；等待和自动唤醒的落地点也未明确。

修订：R1 指定 canonical 协作记录，Snapshot 为只读投影；M6 区分工作/等待/待用户决定与 Mission 状态。唤醒取决于实际宿主能力。对应 T06/T10/T12。

### A12 — P1：替换、撤回与停止的生效范围未闭合

设计变更后 B 可能继续写旧工作区。把 D1 标为旧轮次或发出“停止”消息后立即派 D2，可能让两个执行者同时修改同一范围。

修订：G6 与边界约束保留在途事实；同一写入范围在旧执行已确认停止/结束或已有效隔离之后再派。数据采用撤回可先发生，物理停止另等宿主证据。对应 T14。

### A13 — P1：单 A 部署下隐含要求参与者承担运行时职责

v0.1 虽将 B 的独立 TPlan 描述为可选，M2/T18 仍要求承接端在副作用前机械识别已承接轮次，未说明普通会话如何具备该持久机制；返回记录的字段要求也可能转化为 B/C 必须使用统一运行时。

修订：Core/M1 明确唯一必需的 TPlan 部署在 A。M2/M4/M5 将下行工作说明、自然语言上行结果和 A 侧结构化记录分开；宿主来源映射、A 的发送意图和去重记录承担必要控制。未知投递先查询，宿主自主重投能力单独验证。B/C 可用任意内部工作方式，不写总 Mission、不承担 TPlan 认证/存储/去重服务。R4 增加实现难度和首版范围；T19–T21 验证零 TPlan 参与者、普通回报和任务关联歧义。

### A14 — P2：把 runtime 按需登记误设为用户模式开关

v0.2 的“显式启用/opt-in”没有区分 Agent 提交能力状态与用户选择模式，可能导致每次额外询问模式，或在新轮次没有模式提示时漏掉在途责任。

修订：M1 将任务需求、通信授权、持久恢复状态分别处理。A 根据已授权分工登记能力；已有协作从记录续接；普通任务和仅引用其他会话材料继续原路径。R1 保留受校验的扩展事务与 runtime provenance，已有不兼容 runtime 经明确迁移/交接后接入。T22–T25 覆盖自动选用、参考材料、续接和用户当前会话限制。

### A15 — P1：协作状态完整，仍可能掩盖实际目标漂移

用户最终确认以主会话目标保持为核心。v0.3 的机械验收覆盖任务关联、版本与投递，但 A 即使保留同样的 objective 字段，仍可能被每条反馈牵引，逐步扩大范围或承担原本由 B 负责的局部调试。仅观察游标和状态一致无法评估这种偏移。

修订：重写 Core 的目标与主从关系；M1 复用 Mission 记录目标、责任、验收和当前差距；M4 在原有短循环中直接加入目标关联、范围取舍、角色责任与续接判断，不另增一套控制层。R3 将实际行为验收放在机械机制之前，T26–T29 分别验证无关建议、调试细节、高频反馈和有依据的路径/目标调整。反螺旋自检结论为回到上游目标、重排已有机制的主次，未新增调度子系统。

## Boundary / 后续冻结点

- 先把 T26–T29 的实际目标保持行为设为首要验收；再将支撑用例 T01–T25 转为失败用例，确定 A 侧协作字段与 action schema、幂等冲突、当前状态前提、容量和归档边界。参与者侧采用普通任务说明和回报。
- 宿主接入验证实际 peer 来源、消息投递未决查询、活跃/空闲会话唤起、Guard 事件行为；验证缺口时使用检查点拉取路径。
- 验收保留完整业务结果与异常恢复两组证据，再判断发布和旧任务迁移；ROI Beta 线已停止维护，协作能力按后续正式版本规划。

交付前定位：当前审计提供设计修订和可验证的下一步，供 Owner 选择是否推进完整工程设计。
