# TPlan 协同模式：主会话目标保持与反馈续接

日期：2026-11-17。版本：设计稿 v0.4，以主会话目标保持为首要目标；默认仅 A 启用 TPlan、按任务启用协作能力，已完成同一 Agent 的设计自审，供 Owner 评审。
源码基线：`520376990`；发布对照：`v1.13.0`。本稿提出改造合同，运行时实现和真实宿主验证尚待进行。

## Core / 核心判断

本次改造的核心目标：在多会话协同、异步反馈和反复中断下，主会话 A 持续围绕用户赋予它的目标、责任和验收标准作判断与行动。

A 以总目标的剩余差距选择下一步，判断外部反馈对目标的作用，并在处理后接回有效主线。用户调整目标时明确更新目标与验收；新证据出现时有依据地修订实现路径。

任务委派、反馈收件、版本关联和恢复记录是支撑能力，按其对目标保持的实际贡献实施。首要验收观察 A 的实际任务选择、范围取舍和目标推进；目标文字保持不变只是其中一项检查。

默认部署只要求 A 使用 TPlan。总目标、任务树、委派记录、回执处置与验收均由 A 侧维护；B/C 是普通协作会话，接收任务说明、执行并回报即可。B/C 自行使用 TPlan 是可选的内部组织方式。

用户描述目标、分工和授权即可，日常无需选择“普通/协同模式”。A 根据任务和已有状态使用所需能力；协作启用记录由 Agent 通过 runtime 明确提交。

一份 Mission 持续保存目标、验收与未完成责任。A 的工作焦点和已委派工作的执行状态分开表达；总目标、执行路径与聊天轮次分别管理，帮助 A 处理反馈后继续履行自己的责任。

## Mainline / 正常使用路径

### M1. 先约定责任和可调整范围

启动时先明确 A 的目标、责任边界与完成标准，复用现有 Mission 与对齐字段保存。当前采用的关键决策、目标剩余差距和下一动作保留短摘要，在有意义的反馈处理、长中断或上下文恢复时读取。委派记录引用这份上下文，避免另建一套目标定义。

本例采用 A 设计兼统筹、B 开发、C 审计。角色与具体会话分别绑定，可通过交接更换会话；TPlan 核心使用协调者、执行者、审查者等职责，不硬编码 A/B/C 或三角色流水线。

A 管理任务与会话的对应关系，B/C 保持各自的对话和工作区。B/C 无需安装或启用 TPlan、创建 Mission、运行 TPlan 命令、挂载总 Mission 目录或直接写入其状态。收发使用已授权的现有会话与宿主工具；共同项目文件按实际工作需要共享。

使用入口遵循以下规则：

- 单会话任务默认按普通 TPlan 推进，不增加参与者、委派和等待记录。
- 用户要求 A 统筹其他会话，或任务执行中出现已获授权的实际委派时，A 自动登记相关会话与任务，按需启用协作能力；不额外要求用户说“开启协同模式”。发往其他会话的消息仍依据用户直接给予的通信授权，缺少授权时只确认具体收件会话和工作范围。
- 仅提到其他会话、读取参考材料或收到未关联消息时，先判断是否涉及当前 Mission 的实际协作；关键词本身不触发派工或扩展权限。
- 已有委派在途、回执待处理或结果待验收时，后续轮次从持久记录恢复，不因用户没有重说“协同”而丢失状态。协作收口后，A 可继续单会话工作，历史记录保留。
- 用户要求“只在当前会话做”时，按该范围执行。若已有在途委派，停止新派发，并核对已有执行及回执，按用户要求处理后续；已经发生的执行事实仍保留。

例如：“你负责设计和统筹，把开发任务发给现有 B 会话，把审计任务发给 C，允许它们在本任务中回报”，就已给出分工和通信范围，A 可直接组织协作。“用 TPlan 帮我完成设计”则默认由 A 单会话推进。首次进入协作时只需简短说明分工；只有责任或权限范围变化时再作必要说明。

| 对象 | 谁负责 | 持续记录什么 |
| --- | --- | --- |
| 总目标、范围和验收标准 | 用户确定；A 在既有授权内维护 | 当前有效版本、授权依据、变更理由 |
| 设计及整体路径 | A | 设计决策、依赖、当前采用版本、下一步 |
| 开发任务 | B；A 登记其交付和状态 | B 在普通回复/成果中提供实现、测试、版本、阻碍与设计变更建议 |
| 审查任务 | C；A 登记其原始结论和依据 | C 在普通回复/报告中提供指定版本、审查范围、问题与结论 |
| 总 Mission 的业务状态 | A 统一作语义决定，runtime 提交 | 已采用的结果、任务状态、验收和未完成责任 |
| 通信与会话生命周期 | Codex 等宿主 | 消息投递、会话唤起、执行观测与原生引用 |

A 的 Mission 覆盖用户赋予它的责任：若负责最终交付，就持续到实现和审查满足验收；若只负责设计，就以约定的设计交付条件收口。A 不因收到开发反馈而自动获得额外的实施或发布权限。

协作启动时记录本 Mission 内的委派、双向回报及必要的返修通信授权，以及哪些范围、预算、验收变更需回到用户。正常契约内的解释、取证、返修和继续推进由责任 Agent 完成。

目标与约束需区分：用户要求和权限按授权修改；设计选择随证据修订；技术假设标明待验证条件。发现原假设失效时，A 能更新设计或提出目标变更。

### M2. 委派时交付一份足够工作的合同

每轮委派在 A 侧记录：Mission/任务引用、承接会话、任务目标、当前设计与成果基线、验收条件、允许调整范围、关键依赖、证据要求、回报对象和阻塞时的处理方式。发送给 B/C 的内容是可读的工作说明；只附识别工作所需的简短委派编号/轮次，不要求理解 TPlan schema 或返回固定 JSON。

以一份短摘要加可打开的规格与证据引用为主。B/C 可按需读取相关上游决策；发现合同缺口时提出澄清。A 保留决策和依赖变化摘要，代码调试细节由 B 保存。B 的局部工作较长时可自行使用 TPlan 或其他管理方式；A 仍通过同样的任务说明与回报接收结果，无需同步另一份任务树。

委派使用稳定的身份和轮次，A 侧先记录发送意图，再使用宿主通信工具。只有确认未送达或宿主提供可靠幂等发送时才重试同一意图；结果未知时查询原会话，不新建同目标执行。新版本、重新授权或返修产生可追踪的新轮次。成果记录包括仓库、worktree 或文档位置，以及固定 commit/内容摘要。

A 的记录与适配层负责阻止自身重复派工、归并重复回报。普通 B/C 可依据委派编号和对话历史识别重发，这属于协作提示；传输层自主重投后的机械去重由宿主能力承担。若宿主缺少可靠投递身份，就采用查询核对和暂停未决重发的方式，不要求 B/C 安装持久化接收器。

### M3. 工作焦点与外部执行分开

保留 `active_task_id`，在协同配置下用于协调者当前工作焦点。委派记录引用现有任务节点，另记承接人、轮次、投递事实和成果引用。任务的业务状态仍来自任务树。

A 处理 T2 时，B 可以执行 T1，C 可以审查 T0。收到 T1 的回执时更新 T1 的有关事实；是否转移 A 的焦点，由依赖和影响决定。展示用的委派看板从这些记录生成。

`active_task_id` 的当前 setter 会随任一任务进入 `active` 而移动游标。因此实现时必须新增保留协调者焦点的委派更新入口，并审查相关读写者；仅增加 `owner_session` 字段还不够。

### M4. 收到反馈后走一个短循环

1. **接收**：从宿主返回对象或经核对的会话记录取得来源。A 将普通回复整理为候选回执，关联 Mission、任务、委派轮次、设计/成果版本，保存必要摘要和原文引用。同一来源事件去重。
2. **判断**：A 对照自己的目标、责任、验收与当前差距，判断反馈是否相关、证据是否充分、是否需要改变当前动作。发送者提供的 `impact`、角色名和 `PASS` 都是待核对内容。
3. **采用**：记录与 Mission 有关的处置和理由，例如回答、采用成果、退回修复、要求补证、延后处理、重议设计。范围新增建议根据原目标决定延后、另立候选或提交用户选择。需要变更状态时通过现有事务和决策入口提交。
4. **续接**：从总目标的剩余差距和最新依赖选择继续原焦点、切换受影响任务或等待。切换时说明怎样服务当前目标；恢复记录保留原焦点及下一动作，作为选择依据。

回报的结构化由 A 侧完成，runtime 校验整理后的字段与引用。B/C 提供成果、验证结果、问题和需要的决定即可。身份从宿主会话关联取得；任务和版本从委派记录、原回复及成果核对。若多个未完成委派都可能对应这条回复，或缺少关键版本/证据，A 只补问缺项，保持待关联/待核查状态；其余独立工作继续。

A 按自身责任处理反馈：设计决策由 A 作出，局部实现与排错交回 B，审查判断由 C 承担；A 可为验证关键假设做有界核查。只有用户明确改变分工时才调整责任。连续处理反馈却没有缩小目标差距、补足验收证据或修正关键路径时，沿用 Mission Pulse/反螺旋检查，合并待办、回到主线或回查上游。

| 反馈 | 正常处置 | 对 A 焦点的影响 |
| --- | --- | --- |
| 已有合同能回答的澄清 | 引用合同回答；保留必要关联 | 通常继续原工作 |
| 澄清暴露合同缺失 | 补足由 A 负责的设计决定，更新合同版本 | 依影响判断 |
| 进展或成果提交 | 核对引用，登记成果或送审 | 通常保持 |
| 局部缺陷 | A 判断修复范围，给 B 有界返修任务 | 无关工作继续 |
| 设计假设失效、共享依赖变化 | 标出受影响任务，调整设计和采用版本 | 重新选择下一动作 |
| 超出授权的范围或资源变化 | 整理具体选择交用户 | 其余已授权工作可继续 |

普通更新按批处理；安全、权限、不可逆动作或当前工作即将失效的信号尽快评估。进入下一个具有副作用的动作前，以及交接、验收前，都检查待处理的相关反馈。处理最长等待时间/检查间隔在启动时约定，避免一个长 Step 永久饿死收件箱。

回执的接收确认只表达已收到。常规通信不要求向用户重复发送 ACK；交付、阻塞、需要决策和有意义的变化才形成用户进展更新。

### M5. 交付、审查与验收分别记录

B 提交固定成果后，C 按合同审查该成果。C 可以用普通文本报告审查对象、范围、问题和结论；A 侧生成关联任务、委派轮次、成果摘要、合同/验收版本、审查者和依据的审查记录。A 保留 C 的原始结论并核对适用范围，再提交符合合同的采用和验收记录。C 保有审查判断责任，A 负责记录与整体收口。

是否需要独立审查由任务风险与验收合同确定。示例中的重要功能要求 C 审查；其他低风险任务可使用现有轻量验收。

审查不通过时，A 判断是实现缺陷、设计缺陷、审查依据冲突还是范围新增，给出对应动作。已经明确授权、确定修复范围和轮次预算的返修可以由脚本执行派发；修复目标与验收口径由 Agent 判断。连续返修、跨模块影响或没有新增证据时触发已有反螺旋检查。

采用新成果后，旧审查结论保留为历史。对新成果所需的复审范围由审查责任方明确；旧版本的 PASS 不进入新版本验收。新结果仍使用 TPlan 原有的成功关键任务与 Mission 验收条件，协同配置额外校验当前采用版本和所需审查。

如果任务已完成、总 Mission 仍在进行，新证据确认当前采用成果不再满足验收，则记录该版本的验收失败并阻止总 Mission 收口。需要修复时创建有验收要求的成功关键修复任务，保留原完成历史，修复和复审后更新当前采用成果。已关闭 Mission 的后续发现进入显式后续处置，不自动重开历史 Mission。此路径也要覆盖非当前活动任务和已完成节点。

### M6. 等待、结束轮次和恢复

等待是一种协调执行状态。记录等待哪个委派/结果、恢复条件、最后已处理的回执和下一检查条件。其他可推进任务继续；全部在等待时 A 可以结束当前轮次，Mission 保留未完成责任。

协调执行状态使用 `working / waiting_external / awaiting_owner` 等独立字段，Mission 继续使用现有状态。普通等待外部成果不调用会将 Mission 设置为 `requires_human` 的 `stop_report`；确需用户决定时沿用现有机制。

下一次唤醒时先查最新 Mission、未处理回执、依赖与投递未决事实，再选择下一步。旧焦点如已失效，记录切换理由。TPlan 保存恢复依据，唤醒由宿主提供；没有自动唤醒时以人工/既有检查点续接。

A 更换会话时，完成显式交接，保存未决派发和回执，更新协调者绑定；旧会话停止写入。需要机械排除旧写入者时，由受保护宿主绑定和所有支持的 writer 共同检查交接代次，普通记录里的会话名只作关联。

## Guardrail / 保护主路径的规则

| 规则 | 保护的主路径及误用 | 作用范围 |
| --- | --- | --- |
| G1 来源与权限分离 | M1/M4：把其他会话的内容当成用户新授权 | 来源可确认的参与者只能在已授权任务范围内提供输入；转述和未知来源待核对；权限提升沿现有宿主流程 |
| G2 接收与采用分离 | M4：收到内容立即改状态、重复消息重复派工 | 原始回执是候选事实；采用有独立记录、幂等身份和当前版本检查；语义正确性由责任 Agent 核对 |
| G3 保留现有 Guard | M4：用“旁路反馈”穿过正在开启的用户中断保护 | Guard 开启时主 Mission、证据及协作状态均不写；宿主可暂存传输回执，解除后再导入；暂存本身无业务权力 |
| G4 版本绑定与选择恢复 | M3/M5/M6：旧审查套新代码、处理后盲回原任务 | 每次采用/验收/续接检查相关版本和依赖；旧版本仍可提供新风险线索 |
| G5 未知投递先对账 | M2/M6：发送超时后换号再发 | A/宿主适配层保留原 intent 和原生引用，查询已有会话记录；未确认时暂停该项再派；普通 B/C 不承担持久化去重服务 |
| G6 局部等待与执行撤回分离 | M4/M6：一个阻碍冻结全 Mission，或把请求停止当成执行已停 | 按依赖限定等待；已发送任务保留在途事实，直到观察到结束/停止；共享写入冲突解除后再派同一写入范围 |
| G7 按价值收敛反馈 | M4/M5：机械逐条处理、审计—修复无限循环 | 合并相同对象的非紧急问题，按完整且有界的交付批次审查；无新增价值时回查上游或停止该轮 |

宿主能够验证参与者来源时，可将 peer 事件送入协作收件入口。来源不可区分、仍表现为普通用户中断的消息继续走既有 Guard；Agent 不自行改写标记或解除保护。首版可采用检查点主动读取 B/C 结果、在 Guard 关闭后导入的方式验证协作闭环。

## Example / A、B、C 的一轮协作

本例仅 A 启用 TPlan，B/C 使用普通 Codex 会话。

1. A 设计模块一，在 TPlan 记录 D1：合同 s1、输入 i1、工作区 w1、验收 AC1；向 B 发送工作说明、规格链接和回报要求，自己转向独立模块二。
2. B 交付成果 h1，A 登记后将同一成果交 C 审查。C 审查期间，B 保留 h1；下一批独立工作使用独立范围或 worktree。
3. C 返回 h1 的失败重试缺陷。A 确认属于已定义合同内的实现问题，授权 B 用 D2 修复，自己的模块二继续。
4. B 交付 h2；A 将 h2 交 C 复审。C 对 h2 的指定范围通过后，A 核对其余验收并完成模块一。
5. 如果 C 的发现推翻共享接口假设，A 标记相关设计/实施任务受影响，更新接口与合同版本，再决定继续哪些工作。
6. A 在等待 C 时结束轮次。恢复后读取 h2 的回执和未处理问题；重复到达的 h1 报告只登记一次，其结论按版本处理。

一个下行说明可以是：“请实现模块一（D1，第 1 轮），按所附规格和验收条件工作。完成后回复修改内容、成果 commit/文件、验证结果及遗留问题；遇到合同缺口先提出。”B 的普通回复由 A 核对并录入；C 以同样方式收到固定成果的审查任务。

## Runtime support / 工程改造与证据

### R1. 最小状态与事务归属

新能力只在 A 所使用的 runtime/Mission 中按需登记 `collaboration` 扩展，保留现有树、`active_task_id` 和事务系统。启用由 A 根据 M1 的任务与授权判断，通过受校验的事务入口明确提交，不设置用户必须操作的模式开关。参与者配置不要求 B/C 提供 TPlan 版本、Mission 或命令入口。下列是逻辑合同，不是已存在的 CLI 或冻结字段 schema。

支持此能力的 runtime 应允许普通 Mission 在首次需要协作时，通过合法扩展事务接入，保持目标、既有验收与恢复引用。已经固定到不兼容旧 runtime 的 Mission，先走兼容性检查和明确的迁移/交接路径，再使用新能力；根据任务自动选用能力不改变 runtime provenance 规则。

| 记录 | 最小内容 | 归属 |
| --- | --- | --- |
| 协作配置 | 协调者绑定、参与者/职责、通信授权引用、处理与等待策略 | Mission 的协作扩展 |
| 委派 | ID、任务、轮次、承接者、合同版本、输入/成果引用、依赖、审查要求 | 协作扩展，引用任务树 |
| 投递意图与结果 | 稳定 intent、目标会话、输入摘要、原生回执、已确认/未决事实 | 同一协作扩展；宿主负责实际收发 |
| 收到的反馈 | 来源事件引用、委派/轮次、版本、类型、必要摘要/附件引用 | A 将普通回复规范化后的有界候选回执；保留来源，缺失关联待补 |
| 处置 | 回执 ID、当前状态前提、处理结论、采用结果、决策/证据引用 | 同一持久事务提交 |
| 等待与恢复 | 等待集合、原焦点、下一动作候选、依赖版本、最后处理位置 | 协作扩展；摘要是只读投影 |

一次状态采用须原子提交：回执处置、任务变化、采用版本、所需证据和新投递意图。发送发生在提交意图之后，宿主回执再记录；恢复沿原身份查询或处理。相同事件同内容重放为无变化，相同身份不同内容报冲突。

只读 Snapshot/Pulse/看板从记录生成。收件状态不放进 Snapshot 作为可写事实源。正常接收和处置复用现有 Mission 锁与恢复边界；进程间并发导入只获得机械收件权，整体路线与验收仍由协调责任方决定。

实现合同需冻结容量上限和可读归档规则。到达容量时明确拒绝新的导入，保留宿主来源引用与原命令身份，已有记录仍可查询和恢复；不得静默丢弃待处理内容。首版不引入第二套数据库或队列调度服务。

### R2. 现有代码的接点

| 接点 | 当前事实 | 改造方向 |
| --- | --- | --- |
| `tplan_runtime.py:_event_is_on_current_path`、`_collect_feedback_or_blocker_candidates` | 任务级反馈筛选当前活动节点，普通 feedback/user_feedback 归为同类回溯候选 | 从协作记录收集所有相关待处理任务；按来源、版本、依赖和处置状态生成候选，语义影响交 Agent |
| `tplan_runtime.py:set_task_status` | 任一任务进入 active 会写 `active_task_id` | 委派更新显式保留协调者焦点；验证旧调用行为和新能力的分界 |
| `commit_mission_state` 与 Guard | Mission、证据、trace 和 Guard 使用现有事务/恢复；Guard 保护整份状态 | 协作扩展纳入相同提交和 Guard，加入过期决策前提检查 |
| 完成校验 | 主线要求 success-critical 节点 completed 和合格验收；H1 另有当前采用版本检查 | 新协同任务完成和 Mission close 都校验当前成果、合同版本及 required review，补普通协作的版本合同 |
| 输出与恢复 | 已有共享上下文、只读 Pulse、进展和续接输出 | 加入外部等待与可推进任务；焦点摘要内部默认可用，向用户只报告有意义变化 |
| Q1/Q2/H1 | main 有查询、普通 observation 幂等记录、受控派工/版本验收接点；v1.13.0 中尚无这些脚本 | 复用事务、身份与版本原则；Q2 observation 本身不承担反馈采用/验收，H1 受保护模式按原权限接入 |

普通 Codex 协作使用当前自主模式和用户授权。需要受保护 Owner/reviewer 认证的流程沿 H1 合同，由 Host 实现身份与存储隔离；不把普通会话文本包装成签名凭据。

### R3. 交付顺序和验收

**第一批：完整功能设计。** 冻结事件/采用/版本/投递未决/等待恢复的状态转移、兼容性与宿主能力合同，形成失败用例。下表是该批的最小验收目标。

**第二批：一次完整功能实现。** 在支持该能力的 runtime 上实现按需登记协作状态的事务入口、Pulse、输出和 Codex 适配，再统一做自测与审查。验证新建时已知分工和执行中首次引入委派两种路径；旧 Mission 保持原固定 runtime，兼容、迁移与发布另有明确验证。

**第三批：真实协作闭环验收。** 使用三个已授权会话，明确只有 A 启用 TPlan，B/C 无 TPlan 工具和总 Mission 访问依赖。执行一项有界任务，从普通消息委派到返修、复审和总 Mission 收口；记录宿主实际支持的来源、唤醒、回执查询与 Guard 事件。通过后再评估发布。

验收顺序以目标保持为先：观察多轮反馈后 A 仍在履行哪项责任，选择了什么下一动作、为何相关、总目标还有什么差距。T26–T29 覆盖这一核心行为；其余用例验证支撑它的状态、证据和恢复机制。评审同时检查合理的路径修订，依据是目标关联、证据和权限。

| 用例 | 可观察的通过条件 |
| --- | --- |
| T01：A 在 T2，B 返回 T1 | T1 正确登记；无依赖影响时 A 保持 T2；待处理 T1 不被 Pulse 漏掉 |
| T02：同回执重复/同 ID 异内容 | 同内容仅一次效果；异内容冲突，不覆盖历史 |
| T03：h2 已采用，迟到 h1 PASS | h2 验收未被满足；h1 结论保留为历史 |
| T04：合同澄清实为新设计选择 | 生成有理由的合同修订；原输入与新输入可区分 |
| T05：C 报实现缺陷或设计缺陷 | 分别给出有界返修或上游调整；每条动作有负责人和依据 |
| T06：A 等待后结束/更换会话 | 读取未决派发和回执继续；任务不重派、Mission 不误完成 |
| T07：send 超时/进程在发送后退出 | 查原会话/intent；未知时不创建第二次同目标执行 |
| T08：Guard 开启时收到 peer 结果 | 主状态及证据摘要不变；解除后只导入一次；无自动解锁 |
| T09：T1 失效，T2 依赖 T1 | T2 不盲目续接；独立 T3 可继续 |
| T10：所有任务均在外部执行 | 表达为等待及恢复条件，避免误用 requires_human 或忙轮询 |
| T11：伪造 C/Owner 身份或转述 PASS | 不产生越权决定；核对真实来源、指定审查者及版本 |
| T12：收件/采用/证据提交中断、容量不足 | 同一事务可恢复；重复执行无第二次业务效果；满载不丢待办 |
| T13：无审查或审查范围不足时收口 | 需要审查的任务和总 Mission 保持未完成；低风险旧任务规则仍有效 |
| T14：请求停止 B，但 B 仍运行 | 保留在途状态，保护冲突写入范围，直到真实结束/停止得到确认 |
| T15：切换协调者后旧 A 继续写 | 受保护配置拒绝旧代次；普通协议试用显式要求旧 A 停止写入 |
| T16：一个长 Step 与高频小反馈 | 普通更新被有界批处理；关键问题在下一有关副作用/验收前处理 |
| T17：任务完成后发现当前成果缺陷 | 总 Mission 的验收被阻止；有界修复任务与当前版本复审通过后方可收口；原历史保留 |
| T18：重复派发请求与宿主重投 | A 侧同 intent 不二次派发、异输入冲突；发送未知先查询。宿主有投递去重时验证真实重投；无此能力时明确记录，且不自动重发或把责任转给 B/C |
| T19：仅 A 启用 TPlan | B/C 无 TPlan 安装、命令和总 Mission 访问，仍完成开发—审计—返修；全部状态采用在 A 侧完成 |
| T20：B/C 仅用普通语言回报 | A 保留来源并提取成果、验证和审查范围，核对后推进；不要求参与者补齐 runtime 字段 |
| T21：同会话多委派，回报未标对象 | A 保持待关联并补问对象/版本；不猜测任务、不先计验收；独立工作继续 |
| T22：没有模式口令，任务含已授权分工 | A 自动登记参与者和委派；首次引入协作保留原 Mission 目标、验收与焦点；不额外询问模式 |
| T23：普通任务仅引用其他会话材料 | 继续普通路径；不创建委派、不自行发送消息 |
| T24：恢复协作任务，用户仅说继续 | 从记录恢复在途委派、待处理回执和验收责任；不依赖重新声明模式 |
| T25：用户限定当前会话执行 | 不发起新委派；已有在途事实和结果按明确范围处理，历史保留 |
| T26：多轮无关或越范围建议连续插入 | A 按原目标说明取舍，延后/另列范围建议，继续关键任务；目标、职责及验收变更均有明确依据 |
| T27：局部调试细节持续占据反馈 | A 提取设计/验收相关影响，将实现排错交回 B，并继续自己的任务；有界核查可说明目标作用 |
| T28：高频进展与重复审计意见反复打断 | A 合并处理并接回有效主线；实际行动产生目标相关结果、必要证据或关键路径修订 |
| T29：反馈推翻当前路径，或用户明确调整目标 | 有证据的路径修订保持目标与责任对齐；用户变更被明确记录并传到受影响委派，下一步服务更新后的目标 |

### R4. 单 A 部署的实现难度与首版范围

该模式减少了多份 Mission 的同步、跨会话 writer 竞争和参与者安装适配，改造集中在 A 侧。其工程难度判断如下；这是基于当前结构的工作范围评估。

| 部分 | 难度判断与依据 | 首版安排 |
| --- | --- | --- |
| 普通会话委派与回报 | 较低：当前宿主已有发送、读取、等待会话工具；B/C 接收普通工作说明 | 复用已授权工具，A 维护会话—任务关联，可先以操作约定试用 |
| 总 Mission 的协作记录与反馈续接 | 中等：涉及现有事务、焦点 setter、Pulse 筛选、采用和版本验收 | 在 A 侧实现一个有界功能批次，保留原 runtime 兼容边界 |
| 自然语言回报整理 | 常规结果较直接；歧义和证据缺口需要 Agent 判断 | A 提取、runtime 校验、缺项定向补问；以 T20/T21 验证 |
| 自动唤醒、可靠来源、投递异常恢复 | 依赖宿主：工具可调用与生命周期可可靠观测需分别核实 | 基础路径支持检查点读取和未决查询；自动化能力按实测启用 |

首版不要求 B/C 加入统一 SDK、安装插件或同步各自任务树，也不以增加参与者负担弥补宿主能力缺口。已有的签名验收/受保护写入按需接入，由宿主提供；普通协作会话维持相同的工作与回报方式。

## Boundary / 本稿的使用边界

本稿默认覆盖仅 A 启用 TPlan、单总 Mission、单协调责任方、多普通会话的目标保持与任务协作；同一任务范围只允许一个当前有效的实施委派。能力选择以主会话目标保持为准，新增通用调度能力需单独说明它解决的目标问题。B/C 使用自身 TPlan 是可选项，适配不依赖它。通用多协调者选主、跨主机强制互斥、任意进程取消、多级组织调度留给有实际需求的后续设计。

首版协议试用可先用现有 checkpoint、证据、决策、共享上下文和宿主通信工具。使用说明明确其状态关联由 Agent 执行；新的机械保证以第二、三批验证为准。协作稿不修改当前安装的 Skill、运行中的 Mission 或发行版本。
