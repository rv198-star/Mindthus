# Mindthus v1.16.0：交付收件箱与回发检查

发布日期：2026-11-24。Stable 小版本。上个版本里，执行会话做完工作有时不回发，或者看到主会话正忙，就把结果留在原地，最后要用户来催。这个版本让每次交付都有地方登记、有人负责收取，漏发时也会有提醒。

## 实际发生过什么

`send_message_to_thread` 发给正在运行的会话时不会被拒收，消息会在几十秒内插进对方当前的回合。执行会话因为“主会话正忙”而暂不回发，是它按规则自己做的判断，暂存的结果却没有人去取。另一种情况是消息工具返回成功，目标会话却已经出错，任务根本没开始。

## 这个版本怎么处理

- **收件箱**：执行会话交付时先登记，再发一条消息唤醒主会话。每条记录指名收件会话，只有收件会话能处理，同一件交付只处理一次。主会话正忙时只登记，做完手头的工作再处理；需要等用户决定的事件可以挂起。
- **Stop Hook（可选）**：装在用户级 `~/.codex/hooks.json`。执行会话还欠着交付就结束回合时，拦一次并提醒回发；主会话还有未处理的交付时，提醒它先处理。只作用于这次派工涉及的会话，每个回合最多拦一次。
- **Hook 失效时的心跳**：派工时根据 Hook 实际运行留下的时间戳，判断它是否在工作。没有生效时，主会话给自己挂一个心跳自动化（默认 30 分钟），只检查收件箱和执行会话是否已结束回合，任务结束后删除。实测心跳到期时如果主会话正在运行，这次触发会被跳过，不会插进当前回合，也不会排队。
- **接收确认**：发出消息后检查一次对方是否开始处理。目标会话出错时记为未执行，派工改走已授权的替代方案，交付留在收件箱等待收取。
- **串行交接**：首份派工写明回程、交付位置和收取方式；执行会话中断恢复后能找回待交付事项，交付后让出同一项工作；跨会话消息统一为“发送会话名：具体内容”。

## 验证与升级

新建会话和复用会话两种接力都已在真实宿主走通：执行会话自行登记收件箱并回发，两轮都没有人工催办，主会话也没有同时做同一项工作。Stop Hook 的拦截行为用模拟输入验证，包括无关会话放行、只拦指名的收件会话、非收件会话无法处理交付，以及欠交付的执行会话被拦。它在真实会话中的表现，要在用户启用 Hook 后观察。

产品包版本为 `1.16.0`，TPlan runtime generation 保持 `1.7.0`，已固定旧运行时的 Mission 继续使用原版本。Stop Hook 需要用户自行启用，方法见[收件箱与 Hook 说明](../../skills/codex-dispatch/references/inbox-and-hooks.md)。ROI Beta 已停止维护及后续发布。
