# Mindthus v1.9.1 发布说明

发布日期：2026-09-05

发布 tag：`v1.9.1`

## 版本定位

`v1.9.1` 是 `v1.9.0` SRA minor release 的兼容性 Bugfix patch。

本版不新增独立 Skill、route、judgment owner 或 TPlan runtime generation。它重建并收紧
SRA v0.3 的方法域与运行时合同，使 Lite / Full、资源数量、Bundle、Allocation Ledger、
Reserve、Outcome / Finalization、上下文隔离、证据权威与 Repair 边界保持一致。

## SRA v0.3 方法域修复

- Lite / Full 使用同一个明确的 resource contract；资源的计量方式、容量、候选 Demand、
  单批投入与授权上限保持可比较。
- Full 的 Bundle、Allocation Ledger、Reserve 和 Outcome / Finalization 使用同一组不变量，
  不允许以渲染结果替代分配事实。
- Allocation Ledger 校验候选的累计 Demand，而不只校验下一批单次投入。当前投入已经耗尽需求时，
  后续批次会被阻断。
- 不可分割门槛、序数资源和可计量资源保持各自语义；脚本只验证合同，不计算语义优先级。

## Challenge Projection 与双视图比较

- Challenge Projection 不接收当前路径、既有结论、候选宣传或沉没成本叙事；真实目标、用户约束、
  权限、证据和执行状态仍保留在正确上下文层。
- Challenge 与 situated 视图独立产出 typed judgment，只有结构化差异才触发一次定向
  reconciliation。
- 即使候选集合相同，只要资源数量、Bundle 组成或授权边界不同，比较器也会识别差异并阻止静默
  合并。

## 证据权威、篡改阻断与 Repair

- `run.json` 只作为缓存；Trace 与 Agentic Judgment 是权威记录。
- prepared-input anchor 必须来自完整 Trace 或包含完整锚点的 run cache。删除 Trace 后，仅凭
  schema-compatible `run.json` 不能启动 Repair。
- Prompt、Schema、Dispatch、Command、Receipt、Final Decision 和 Trace 的完整性失败都会阻断
  最终化，而不是被缓存或渲染结果掩盖。
- Repair 只重建可验证的派生产物；raw input 和 Agentic Judgment 不属于可改写范围。

## 独立验收

在 `origin/main@1a48f70f` 上以 fresh context 重新执行此前发现的两个反例：

1. candidate demand 为 1、current allocation 为 1、next tranche 仍为 1 的累计 Demand 反例；
2. raw input 改动、Trace 缺失、`run.json` 仅满足 schema 的 prepared-input anchor 反例。

两者均按预期被阻断。完整 unittest、Test Lifecycle、`git diff --check` 与 Stable 全包构建通过。
这些结果支持本版合同与门禁覆盖的行为，不证明普适路由正确、最优 ROI、生产收入或长期转化效果。

## ROI Beta 同步发布

Mindthus 按 Stable release 默认规则同步提供 `v1.9.1-roi-beta` supplemental experimental asset。
Beta 从精确 `v1.9.1` Stable shared core 组装并继承本次 SRA 修复。ROI runtime delta、独立
identity / namespace 与历史 ROI.2 3L5S Anti-Spiral correction 保持不变；本版没有新增
Beta-specific 自然唤醒率、相对胜率或 Token ROI 声明。
