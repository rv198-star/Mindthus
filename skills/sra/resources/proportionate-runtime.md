# SRA: low-cost judgment and controlled allocation

## Mainline

For an ordinary reversible choice, answer from the current authorized context: what must
be preserved, where the next useful resource goes, what waits, and when to reconsider.
A short conversational recommendation is sufficient when no audited authorization is
requested. Do not build a run simply to prove that the method was used.

When a controlled allocation is needed, keep one canonical resource/authorization model:

1. Agentic intake extracts current goals, constraints, resources, candidates, dependencies
   and evidence from authorized sources. Read available sources before asking again.
2. `draft_sra_context.py` supplies deterministic structure and lists missing input. It does
   not understand natural language, invent facts, judge necessity or grant permission.
3. Prepare and record judgments through the existing runtime, with the appropriate review
   depth and calibration. `ready_for_prepare` means shape-ready, not decision-ready.
4. Render a short checked card; use `--view full` or JSON for the complete source.
5. Re-rank only on an explicit new request or relevant change, using refreshed context.

## Value and risk

Keep the user's real objective and horizon. Unknown and delayed value is not zero.
Safety, dignity, care, commitments and sustainable capacity may be protected constraints,
not optional low-ROI tasks. Maintenance, learning and reserve may be investments in future
viability. They still need a bounded reason; “survival” cannot justify unlimited spending.

Compare complete useful tranches, including complementary work and fixed thresholds.
Small quick wins have no automatic precedence. Neither does a direction/bottleneck label.
Use qualitative judgments when a common numerical currency would be invented.

The cost of another analysis step should be justified by its likely effect on the next
choice. Execution duration alone is not the ceiling: a seconds-long destructive action
can have a large error cost. Missing authority requires authority, not another model.

## Version-bound calibration policy

Legacy v0.3 raw inputs without `execution_policy` retain their prior conservative view
selection and deterministic replay. New extensions use the explicit v0.4 input version,
so old programs reject them rather than silently ignoring the new policy. The engine and
legacy derived artifact schemas are shared; this is not a second allocation engine.
Fresh intake drafts default to v0.4; explicitly supplied v0.3 input stays unchanged.
New inputs include:

```json
{
  "schema_version": "sra.decision-context-input.v0.4",
  "execution_policy": {
    "version": "sra.proportionate.v1",
    "risk_level": "ordinary_reversible",
    "assessment_basis": "Current request and evidence show a reversible, bounded validation-only action."
  }
}
```

`risk_level` is `ordinary_reversible`, `consequential`, or `unknown`. It is a sourced
Agentic assessment, not a script-proven fact. Missing/invalid policy fields fail validation.
Intake defaults to `unknown`, never an invented low-risk assessment.

| Need | Depth | Default calibration |
|---|---|---|
| One bounded, ordinary reversible choice, clean context | Lite | single |
| Multiple bundles/resources/fixed thresholds, explicitly ordinary reversible, clean | Full | single |
| Uncertain or consequential risk | Lite or Full as required | dual |
| Contamination, prior conclusions, advocacy or sunk-cost evidence | Lite or Full | dual |
| Major commitment, irreversible exposure or other non-structural escalation | Full normally | dual |

Coverage remains separately controlled by omissions and coverage signals. Existing
explicit, authority-bound downgrade rules remain in force; an override is visible in the
result and is never silently generated by intake. Single Full keeps all Full bundle,
resource, dependency and outcome checks and never claims independent corroboration.

Changing policy or facts creates a new run; Repair never upgrades old raw input.

## Commands

```bash
python3 skills/sra/scripts/draft_sra_context.py --input current-context.json --output draft.json
python3 skills/sra/scripts/prepare_sra_run.py --input draft.json --dir /tmp/new-sra-run
# Run the prepared required review(s), then use record_sra_judgment.py as before.
python3 skills/sra/scripts/render_sra_decision.py --dir /tmp/new-sra-run --view card
python3 skills/sra/scripts/render_sra_decision.py --dir /tmp/new-sra-run --view full
```

Intake writes only a new draft file with exclusive creation. It does not create a run or
write Mission state. Unknown dependencies stay missing; `[]` must be an explicit caller
declaration. No timestamps, approval, capacity, outcome, feasibility or priority is guessed.
Errors name missing surfaces for the Agent to resolve from evidence; they are not a form
the user must fill. `--json` still returns the original checked final decision.

New policy runs default to the card in the CLI; legacy runs keep the full rendering.
Safety-critical constraints, quantities, windows, ceilings, dependency states, reserve
release conditions, downgrade authority and no-start states remain visible. Card length
can grow when those boundaries are necessary; it is not a fixed word-count target.

## Shared completion criteria

Use `completion_criteria.version = sra.completion-criteria.v1` with `items` containing:
`criterion_id` (neutral `CR-...`), `revision`, `subject`, `observable_result`,
`evidence_requirement`, `window`, `source`, and `content_hash`. Intake can compute the
hash when all semantic fields are supplied. Candidate `completion_criterion_ids` declares
which criteria apply. Common criteria are sourced before the independent views, with
neutral wording rather than prior recommendations or active-path identity.

A new tranche may replace `completion_signal` with `completion_criterion_ref`, containing
`criterion_id`, `revision`, `content_hash`, and its own `packet_hash`. The schema binds
the reference; the domain validator checks candidate scope and window. Two contradictory
condition carriers cannot coexist. Each view still independently chooses its criterion,
resources and action. It may use the conservative free-text branch for a new or unbound
condition; the table does not force agreement.

A shared reference removes wording-only differences. Different quantity, window,
criterion, dependency, start condition or other commitment still conflicts. New policy
comparisons expose precise `conflict_paths`, while preserving existing conflict-field
resolution ownership. Renderer expands the same checked criterion. Agreement proves
neither that the criterion measures the real goal nor that the allocation is optimal.

## Explicit re-ranking

```bash
python3 skills/sra/scripts/rerank_sra_context.py --parent /tmp/old-sra-run \
  --input refreshed-context.json --run-id next-resource-window \
  --reason "Capacity or decision-relevant evidence changed" --output rerank-draft.json
```

The refreshed input must be explicit. The command checks the parent, records immutable
parent raw-input and final-decision hashes, and produces a new draft. It does not copy
parent priority, feasibility, satisfaction, approvals, selected bundles or allocation.
Refresh capacity, commitments, source currency, candidates, dependencies and risk. Old
facts may remain relevant only after current assessment; this tool does not certify their
freshness. The parent remains unchanged, and lineage is withheld from judgment packets
so old conclusions gain no new authority. A new prepared run starts with no judgments.

No automatic trigger monitor, background reranking, Mission mutation or TPlan handoff is
introduced. This is explicit allocation support, not execution permission.
